# 2026-10-20

## Materials: a model now carries its own texture

Three layers landed, each verified against real data rather than by eye.

### RW4 containers hold their own textures

8,915 of 9,368 RW4 files in `Spore_Graphics` contain a `0x20003` Raster object. Layout is
32 bytes: format at 0, width u16 at 12, height at 14, mipmap count u8 at 17, data object
index at 28. Formats measured: DXT5 4,769, DXT1 2,366, `A8R8G8B8` 1,555, `L8` 220, DXT3 5.

`--rw4-textures` decodes all 8,915 and prints per-resource digests; `tools/rw4_texture_digest.py`
reproduces them independently. Diff: **0 of 8,915**. That needed `decode_pixels` in
`raster.rs` (format + size + payload, no container), DXT3 and L8 support, and `rw4::texture`.

### Two bugs found by the comparison, both real

1. **DXT3 must not swap endpoints.** Forcing four-colour mode by swapping `c0`/`c1` when
   `c0 <= c1` also swaps the two blend weights. All 5 DXT3 resources mismatched until the
   swap was removed and `force_four` was passed to the colour decoder instead.
2. **Bevy's default sampler clamps.** UVs are not in 0..1: one creature part measured
   -3.5..0.98. With clamping every negative UV collapses to the first texel, so the model
   rendered as one flat colour. Fixed with an explicit `Repeat` sampler on the `Image`.
   Diagnosed only by adding a checkerboard mode (`--shot ... checker`), because a white
   model and a mis-sampled model look identical.

Also: the checkerboard must use small cells (8 px). Parts occupy a small patch of their
atlas, so a coarse pattern reads as flat colour and proves nothing.

### A `BaseResource` offset is relative to `p_buffer_data`

Every other object's offset is absolute. This produced a false negative: the comparison
script used the offset as absolute, decoded 8,915 textures with no error, and differed on
every one, because the wrong offset still lands on valid block data. Both readings give a
plausible image; only a digest comparison catches it.

### Prop keys: little-endian, and not (group, type, instance)

The three words of a prop `key` are **little-endian** in an otherwise big-endian format.
Read big-endian, a gmdl key's type comes out `0xE5BCE600` instead of `0x00E6BCE5`.

The words are `(instance low, type, instance high)`, and the instance is `high << 32 | low`.
Read as `(group, type, instance)` nothing resolves: 0 of 4,403 model references. Reassembled,
all of them do.

Prop idents are hashes and the strings are in the executable, so names are not recoverable.
Roles are measurable, and that is enough: `0x00F9EFBB`..`BE` are a four-slot LOD chain
(1,162 / 1,095 / 1,095 / 1,051 props in `Spore_Content`), `0xD124FCE4` and `0xD124FCE7` are
the colour maps (153 props), `0x00B2CCCB` is the parent.

`PropTree::model()`, `models()`, `textures()`, `parent()` and `PropValue::key()` expose
this. `--prop-models` counts it: 1,162 props in `Spore_Content` name a model, all 1,162
resolve in the package, 153 carry a texture.

**Gap, measured:** the other 1,009 name a parent that is not in the package. All of them are
in `PatchData` or `Spore_Graphics`. Following that needs multi-package loading.

### What the screenshots showed

`--shot <pkg> <out.png> 0 "" <prop-hex>` renders the model a prop names with the prop's
texture: a complete plant, then a coloured insect part with reds and blues. Checker mode on
the same model shows the UV map correctly per leaf, which is what ruled out a UV bug.
