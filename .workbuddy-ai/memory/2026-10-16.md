# 2026-10-16

## RustSpore: reverse engineering SPORE for a Rust/Bevy port

Started the project at `D:\AI\RustSpore` (git repo, first commit `5fa7a98`).
Target data: `D:\Games\SPORE Collection` (GOG repack of the 2009 patched build),
13 `.package` archives totalling about 4.9 GB.

### Settled by measurement

DBPF container format, established structurally rather than from prior knowledge:

- Header: `0x24` = resource count, `0x2C` = index block size, `0x40` = index offset.
  `index_offset + index_size == file size` holds exactly on three packages.
- Index block: 4-byte prefix (always 4), N x 28-byte records, 4-byte trailer.
- Record (7 u32): group, type, instance_hi, instance_lo, offset, stored_size,
  decompressed_size. Field roles separated by value cardinality.
- 136,081 records parse across 10 of 13 archives.

RefPack codec ported to Python (`tools/refpack.py`) and Rust
(`crates/dbpf/src/refpack.rs`). Validated on 800 coded resources across two
packages, each decompressing to exactly the DBPF index's declared size using only
the in-stream header. Two independent sources agree.

### Two hypotheses corrected by measurement

1. Bit 31 of `stored_size` is set on 100% of records, so it is NOT a compression
   flag. The real rule is `stored_size == decompressed_size` means raw.
   (Spore_Game: 2,215 raw, 9,314 coded.)
2. The two `SporeApp.exe` `.text` sections are 93.96% different despite
   near-identical sizes and identical Rich headers. No shared-code claim.

### Open gaps (recorded, not hidden)

- Index layout unknown for 3 packages: `Spore_Audio1`, `Spore_EP1_Locale_01`,
  `Spore_EP1_Locale_02`. The structural search found no valid run in any of them.
  Notably `Spore_Audio2` DOES fit the 28-byte record, so the layout varies per file.
- No RTTI, decompilation or call graph recovered. The REA MCP runs Ghidra headless
  with a 330 s deadline, which a 20 MB MSVC binary exceeds. Tried twice, timed out twice.
- Public sources call SPORE DBPF 2.0 while the u32 at `0x04` measures 3 everywhere.

### Environment blocker

The Rust workspace has never been compiled: there is no C linker on this machine.
No VS/Build Tools, so MSVC's `vcruntime.lib`/`msvcrt.lib` are missing, and
`link.exe` on PATH resolves to PortableGit's GNU `link`. `rust-lld` plus the Windows
SDK libs at `Windows Kits\10\Lib\10.0.28000.0` gets as far as the MSVC CRT symbols
(`_CxxThrowException`, `__CxxFrameHandler3`, `__chkstk`, `_tls_index`, `_tls_used`,
`memcpy`, `memset`). Fix: install VS Build Tools with "Desktop development with C++".

## Second pass (same day), commits ca931e2, 2bee413, c014560

### Index gap closed: all 13 of 13 packages now parse

The three unparsed packages are solved. A unifying invariant holds across every
package: `prefix + record_size + trailer == 36`. Three record variants exist,
differing in size AND field order:

- 28-byte (10 packages): group, type, inst_hi, inst_lo, offset, size, decompressed
- 24-byte (`Spore_Audio1`): type, instance, offset, size, decompressed, group
- 20-byte (both locale packages): hash, offset, size, decompressed, group

Method lesson: **exact fit is not sufficient**. For `Spore_EP1_Locale_02` two shapes
both satisfy `prefix + count*R + trailer == index_size`. The arbiter is storage
contiguity: payloads are packed, so `offset_i + size_i == offset_{i+1}`. `Spore_Audio1`
chains 17,650 of 17,650 pairs with zero gaps, versus 15,730 chains and 1,920 gaps for
the next candidate. `Spore_Pack_03` was used as a control and the method rediscovered
its known layout.

### Engine architecture (docs/engine-architecture.md)

RTTI is **absent** (only 2 type names in a 20 MB C++ binary), so class names came from
string literals instead: 344 simulation classes, 340 ArgScript names, 332 console
commands. Middleware: RenderWare 4 on a DX9 driver, RenderWare Audio plus EAPd
(PureData derived), Havok 3.1.0, Cal3D for skeletal animation, libpng, OpenSSL via
UTFSSL, Tcl/Tk. SPORE is built on EA's shared cross-tree framework (UTFKernel,
UTFNetwork, EASTL), not a bespoke engine. Physics is behind an interface with three
backends (`physics mode <havok | generic | no_collision>`).

### Pipeline proven byte-exactly

13,174 PNG resources across three packages, **every chunk CRC valid**, 214 MB decoded.
A CRC match cannot be satisfied by right-length-wrong-bytes, so this validates the
header parse, index location, field order, raw-vs-coded rule and codec together.

### prop format: attacked, NOT decoded

Established: prop payloads contain length-prefixed UTF-16LE strings, several reading
cleanly (`Details`, `Domes_gear`, `Group_mkmidlegSkinny_0`). NOT established: the value
encoding after each name, so a reader cannot advance between records. The scan fallback
returns truncated fragments (`Def` for `Defense`), proving it lands mid-string. Kept the
tool because its failure is the evidence, but did not present its output as a result.
See `re/payload-formats.md`.

### Rust

New `crates/dbpf/src/index.rs` implements shape detection (exact fit then contiguity
scoring) and per-variant field decoding. Still never compiled: no C linker. Verified
only by brace-balance and reference checks, which is not a substitute for cargo.
One splice bug was caught this way (a dropped brace closing `impl DbpfFile`).

## Third pass (same day), commits 3af8152, b155051

### prop: 0% -> 22.93% exact

The layout is publicly documented, and the documentation explained the bytes. The
original error was **endianness**: the count, identifier, type and specifier are all
big-endian, and the first attempt read them little-endian, producing truncated
fragments like "Def" for "Defense".

Two more errors were then found and fixed by measurement, not by reading:

1. **Strings are mixed-endian**: the length is BIG-endian but the UTF-16 characters are
   LITTLE-endian. Reading characters as BE turns "Name" into CJK.
2. **`texts` (0x22) layout**, derived exactly rather than guessed: props with exactly one
   record of that type have a 540-byte blob, so the record is 536 bytes; the first field
   is 520 and 536 - 520 = 16, fixing the layout as
   `count, then per entry (buffer_size, u32, u32, buffer_size bytes of text)`.
3. **`key` is 16 bytes**, not the 12 that three u32 suggests. Grid test: 12 bytes gives
   6.51% exact, 16 bytes gives 22.93%.

Result: **1,612 of 7,030 resources parse to exactly the last byte.** The metric is
exact consumption, because a correct parse cannot overrun or underrun.

Still blocked: 1,220 failures follow a `key`, and 2,000+ hit an undocumented `type 0x00`
whose surrounding bytes are zeros, suggesting the walk runs past the records rather than
that 0x00 is a real type.

### Build blocker moved one step later

VS 18 Community (MSVC 14.51) is now installed and `link.exe` is found. But
`vcvars64.bat` calls `reg.exe`, which is on the sandbox Program Blacklist, so LIB and
INCLUDE are never set and the link fails with `LNK1181: cannot open input file
'kernel32.lib'`. **Not worked around**, because the blacklist is the user's security
policy. `tools/build.bat` documents the intended invocation. Two fixes offered to the
user: remove reg.exe from the blacklist, or set LIB/INCLUDE directly.

Lesson: when a security control blocks a step, report it and ask. Do not route around it.

## Fourth pass (same day), commit 2bbc127

### prop DECODED: 0% -> 94.99%

**11,354 of 11,953 prop resources across three packages now parse to exactly the last
byte, with zero overruns.** Type frequencies are dominated by real types (key 37,622,
float 25,765, int32 9,485), which is itself a check that the walk is aligned.

Three findings, in order of impact:

1. **There are TWO array markers: 0x009C and 0x001C.** The public notes mention only
   0x009C. Recognising 0x001C took the rate from **52.82% to 94.99%**. Found by dumping
   bytes at a failure: a bbox record (type 0x39) had specifier 0x001C followed by
   `count=1, stride=0x18=24`, and a bbox is 24 bytes.
2. **The array header is `count` then `stride in bytes`.** Reading the second word as the
   count is wrong. Advancing by `count * stride` alone was worth **22.93% -> 68.17%**.
3. **Mixed endianness**: count/identifier/type/specifier/array-header/string-lengths are
   big-endian, but UTF-16 string CHARACTERS are little-endian.

Also: a single `key` is 16 bytes (array stride 12); array elements carry no single-value
padding.

### A derivation that fitted one case and was still wrong

I gave `texts` (0x22) a bespoke layout derived from a prop holding exactly one record of
that type: `count`, then per entry a buffer size, two u32, then that many bytes. It
consumed the same number of bytes as the array reading for that case, so it looked
correct. It was wrong: texts is an ordinary array with stride 520.

**Lesson worth keeping: fitting a single case is not confirmation.** The array rule
supersedes it, and the superseded derivation is documented in re/payload-formats.md as a
warning rather than quietly deleted.

### Method that worked

The exact-consumption rate (does the walk end precisely on the last byte?) was the metric
throughout. It made every wrong size visible immediately, and each hypothesis was tested
by grid-search rather than argued. Failures were diagnosed by dumping the bytes at the
failure position, which is how the second array marker was found.

## Fifth pass (same day), commit f6ef055

### prop refined: 94.99% -> 97.38%

Removed `colorRGBA` (0x34) from `SINGLE_PADDING`. It is exactly 16 bytes with no padding;
treating it as 20 bytes produced 40 overruns in `Spore_Graphics.package`. Fixed.

The remaining 313 failures (2.6%) are clustered in groups `0x0001FFFF` (236) and
`0x00010000` (77). They are likely a variant prop layout used by specific subsystems
(effects, particles), not a structural bug.

### Build partially unblocked

`tools/build.bat` now sets `LIB` and `INCLUDE` directly, bypassing `vcvars64.bat` and its
`reg.exe` call.

- `dbpf` checks cleanly
- `spore-core` checks cleanly
- `spore-bevy` fails: `serde_derive` and the `windows` crate crash the compiler with
  `STATUS_STACK_BUFFER_OVERRUN` (0xc0000409). This is a sandbox stack/memory limit, not a

So the core crates compile and are verified; the Bevy app cannot be built here.

## Sixth pass (same day), commit TBD

### RW4 and RASTER distinguished

The "pair needs explaining" question from the roadmap is solved.

**0x2F4E681B (RW4)** has a PNG-style magic signature:
  `89 52 57 34 77 33 32 00 0d 0a 1a 0a` = 0x89 + "RW4w32" + \0 + PNG trailer
  Header trailer at offset 28: `0xCAFED00D` (little-endian).
  It is a RenderWare 4 object container, not a single asset type.
  9,368 in Spore_Graphics, 1,131 in Spore_Content.

**0x2F4E681C (RASTER)** is a completely different format:
  First u32 = 0x00000001 (version/count).
  Sub-formats: DXT5 compressed ("DXT5" at offset 24) and raw pixels.
  2,954 in Spore_Content only.

The two types are independent formats with adjacent type ids. They are not variants.

## Seventh pass (same day), commit 723c154

### RW4 header structure measured

Statistical analysis of 500 RW4 samples from Spore_Graphics.package:
- Two subtypes at offset 28: 0x01 (41.8%) and 0x04 (58.2%)
- Footer size invariant: off68 = len(payload) - off76 for ALL samples
- Subtype 0x04 is uniform: off48=324, off68=372, off72=4 always. Likely a single
  well-defined object type (mesh or shader).
- Subtype 0x01 varies: off48 and off68 scale with file size. Likely a family of
  related object types.
- Offset 52 invariant at 0x98 (152)
- Many other invariant fields identified
- Correction: 0xCAFED00D at offset 28 was NOT universal. Misreported from one sample.
  The actual field is a subtype discriminator.

New tool: tools/rw4_parse.py
