# 2026-10-16

## RustSpore: reverse engineering SPORE for a Rust/Bevy port

Started the project at `D:\AI\RustSpore` (git repo, first commit `5fa7a98`).
Target data: `D:\Games\SPORE Collection` (GOG repack of the 2009 patched build),
13 `.package` archives totalling about 4.9 GB.

### Settled by measurement

DBPF container format, established structurally rather than from prior knowledge:

- Header: `0x24` = resource count, `0x2C` = index block size, `0x40` = index offset.
  `index_offset + index_size == file size` holds exactly on three packages.
- Index block: 4-byte prefix (always 4), N x 28-byte records, 4-byte trailer.
- Record (7 u32): group, type, instance_hi, instance_lo, offset, stored_size,
  decompressed_size. Field roles separated by value cardinality.
- 136,081 records parse across 10 of 13 archives.

RefPack codec ported to Python (`tools/refpack.py`) and Rust
(`crates/dbpf/src/refpack.rs`). Validated on 800 coded resources across two
packages, each decompressing to exactly the DBPF index's declared size using only
the in-stream header. Two independent sources agree.

### Two hypotheses corrected by measurement

1. Bit 31 of `stored_size` is set on 100% of records, so it is NOT a compression
   flag. The real rule is `stored_size == decompressed_size` means raw.
   (Spore_Game: 2,215 raw, 9,314 coded.)
2. The two `SporeApp.exe` `.text` sections are 93.96% different despite
   near-identical sizes and identical Rich headers. No shared-code claim.

### Open gaps (recorded, not hidden)

- Index layout unknown for 3 packages: `Spore_Audio1`, `Spore_EP1_Locale_01`,
  `Spore_EP1_Locale_02`. The structural search found no valid run in any of them.
  Notably `Spore_Audio2` DOES fit the 28-byte record, so the layout varies per file.
- No RTTI, decompilation or call graph recovered. The REA MCP runs Ghidra headless
  with a 330 s deadline, which a 20 MB MSVC binary exceeds. Tried twice, timed out twice.
- Public sources call SPORE DBPF 2.0 while the u32 at `0x04` measures 3 everywhere.

### Environment blocker

The Rust workspace has never been compiled: there is no C linker on this machine.
No VS/Build Tools, so MSVC's `vcruntime.lib`/`msvcrt.lib` are missing, and
`link.exe` on PATH resolves to PortableGit's GNU `link`. `rust-lld` plus the Windows
SDK libs at `Windows Kits\10\Lib\10.0.28000.0` gets as far as the MSVC CRT symbols
(`_CxxThrowException`, `__CxxFrameHandler3`, `__chkstk`, `_tls_index`, `_tls_used`,
`memcpy`, `memset`). Fix: install VS Build Tools with "Desktop development with C++".
