### Two real bugs, found because the tests finally ran

1. `refpack::tests::end_of_stream_marker_with_no_literals_produces_nothing` expected
   `"abc"` from `[0xFC, 'a','b','c']`. `0xFC` has low two bits 0, so it emits no trailing
   literals. The decoder was right; the test was wrong. Now two tests: `0xFF` emits three
   literals, `0xFC` emits none.
2. The decoder returned a short buffer as success when the end marker arrived before the
   declared output size. Added `RefPackError::Incomplete { produced, declared }`. This
   matters because "decompresses to exactly the declared size" is the invariant the codec
   was validated on, so silent under-production would hide truncated resources.

The gmsh fixtures also declared 14 vertices while writing 36 indices; adding the
`index < vcount` check (which the Python validator always did) exposed it. Fixtures now use
12 indices, which is 4 triangles.

## Format work (earlier today)

### gmdl `0x00E6BCE5`: 96.86% -> **100% (4,209/4,209)**

The last 132 samples were not a variable-size blob. Shader data `0x238` is a
**single byte**. Reading it as `u32 size` then `size` bytes made the reader
consume the byte plus the following `count1` field, so the pair read as a
plausible size: the first sample had `0x11` + `count1 = 1` = `0x111` = 273.

How it was found: not by semantics but by arithmetic. Part records are a fixed
132 bytes (`0x38` + `0x38` + 4 + 12 + 4). Walking 132-byte blocks backwards from
the 12-byte footer landed on five records each ending in a 12-byte all-`0xFF`
key, which put `part_count` at 10789 while the bogus size had left the reader at
11053. The `0x238` byte explains the 1-mod-4 payload sizes I had noticed earlier
(281, 273, 297, 777) and the "1-byte shift" that made the u32 array align cleanly.

Fixes: `tools/gmdl_full.py` (`SHADER_DATA_SIZES[0x238] = 1`), `gmdl.rs`
(`0x238 => r.take(1)`) plus a regression test that builds a trailing section with
`0x238`.

### RW4 `0x2F4E681B`: per-object payloads **100% (10,797/10,797)**

`tools/rw4_objects.py` decodes every section's object by type code and requires
consumption to equal the section `data_size`. All 10,797 pass, zero unknown
types, zero mismatches. One type code is not in the public add-on: `0x7000B`,
a fixed 32-byte object, measured by inspection.

`rw4.rs` was rewritten. The old module was wrong twice: it read the container as
big-endian and invented a "subtype" at offset 28. The fields are little-endian
and offset 28 is the RenderWare type code. The module now parses the container,
resolves each section's range, and implements `object_extent()` for every type
code, so `all_objects_exact()` is checkable in Rust.

### bem `0x1A99B06B`: 65.1% -> **100% (1,733/1,733)**

The first RLE section's decompressed size is **128**, not 68. My transcription
of the version rule was inverted. The failure was invisible at first because a
68-byte read stops early and the second section resynchronises on the next chunk
boundary: 1,128 samples "passed" with 68, and 605 failed. 128 works for every
sample. New `bem.rs` with 8 tests.

### snr `0x01A527DB` container (measured, not codec)

The first 4 bytes are a tag, not a u32: byte 0 version (1/2/4/5), byte 1 flags
(00/04), bytes 2-3 the sample rate as a **big-endian u16** (ac44 = 44100,
5622 = 22050, bb80 = 48000). That is why the old note said "BE u32 ~0x05005622":
that is the tag read in the other endianness. Then BE byte rate at +4, BE
declared length at +8, payload to EOF. The payload is not self-delimiting, so
its extent comes from the resource boundary; the declared length is a decoded-PCM
byte count, equal to `size - 8` on 2,776 of 2,898. 11 resources are 8 bytes
(tag + one BE float, no payload). 83 set bit 0x20000000 in the byte-rate field
and use a variant header not decoded. `tools/type_01a5_validate.py`.


## Lesson worth keeping

Three blockers fell to arithmetic or to running the thing, not to semantics: a 132-byte
stride walked backwards, a 1-mod-4 payload size, and a test that had never been executed.
When a length field yields a plausible but unworkable value, check whether it is actually a
shorter field overlapping its neighbour. And when a suite has never run, assume it is red.

## The viewer renders real assets

The data layer now feeds the renderer. `rustspore --viewer <package>` opens a package and
renders one mesh at a time with a texture; `--shot <package> <out.png> [index]` writes a
PNG and exits so the pipeline can be checked from a shell.

Verified with real data, not by eye alone:

- **DXT1/DXT5/raw decode**: `--raster-digest` vs `tools/raster_digest.py`, byte-identical on
  **2,954 of 2,954** RASTER resources in `Spore_Content`. The first diff attempt looked
  like every line differed, which was Python's CRLF stdout; `diff --strip-trailing-cr`
  fixed the comparison, not the code.
- **gmsh**: `--gmsh-digest` vs `tools/gmsh_digest.py`, identical on **2,422 of 2,422**,
  covering positions, indices, normals and UVs. The packed-normal unpack had to use an
  f64 intermediate (`(b as f64 / 127.5 - 1.0) as f32`) to match the Python bit for bit.
- **Mesh conversion**: `--mesh-selftest` converts 2,422 gmsh and 4,208 gmdl with zero
  failures, 27.6M vertices and 23.5M triangles. The single "failure" was an 80-byte gmdl
  with zero meshes, which is a valid empty placeholder, now counted separately.

### What the formats actually meant

gmsh attribute sections are `[semantic, set, element type, index]`, and the semantic
numbers are **not** D3DDECLUSAGE: `2` is the normal, which D3D calls `3`. Established by
geometry, not naming (`tools/gmsh_semantics.py`): mean |dot| with the computed face normals
is 0.725 for magic `02000301` (float3, unit length) and 0.336 for `03000301`, so the first
is the normal and the second the tangent. UVs are `08000202`, float2, on 91.9% of meshes.
Only 24.4% carry float3 normals; 2,073 carry them as packed UBYTE4 in `02000701`, decoded
as `b / 127.5 - 1`, which also measures unit length at mean |dot| 0.710. The remaining 11
meshes have none, so normals are computed area-weighted.

gmdl vertex elements are real D3DDECLUSAGE: position `type 2 usage 0`, normal
`type 5 usage 3` (UBYTE4, signed decode), tangent `type 5 usage 6`, UV `type 1 usage 5`,
blend indices `type 5 usage 2`, blend weights `type 8 usage 1`. All on stream 0, so the
multi-stream case never occurs in this install.

### One real data defect

Some gmdl models store `NaN` in the UVs of unused vertices (24 of 25,109 in one model).
A single NaN poisons interpolation across a whole triangle, so non-finite shading values are
replaced with zero and counted in `MeshData::sanitised` (8,958 across `Spore_Content`)
rather than passed to the GPU. Non-finite **positions** still fail the conversion.

## RW4 geometry, including blend shapes

`from_rw4` now turns RW4 containers into meshes. The container is an object table, and
every object reference is a **section index**, not an offset: `index >> 22` selects the
index space (0 = object, 1 = "no object", 2 = sub-reference).

Object layouts, all little-endian:
- `VertexDescription` (0x20004): 3 ints, `u16` element count, byte, byte vertex size, int,
  int, then elements at **offset 24**. Reading elements at 20 produced plausible garbage
  (stream 257, offset 20737) and was the one real bug; a unit test now pins the offset.
- `VertexBuffer` (0x20005): description index, int, base vertex, count, int, vertex size,
  data index.
- `IndexBuffer` (0x20007): int, start index, primitive count, usage, format (101 =
  INDEX16), primitive type, data index.
- `Mesh` (0x20009): int, primitive type, index buffer, triangle count, vb count, first
  index, primitive count, first vertex, vertex count, then the vb indices.
- Vertex data and index data are `BaseResource` (0x10030) objects, whose `p_data` is
  relative to `p_buffer_data`.

`Mesh.primitive_count` is the **index count**, not the triangle count (1392 = 3 x 464).

**Blend shapes.** 1,391 of 7,402 RW4 meshes reference `1 << 22`, the "no object" sentinel,
meaning their geometry is in a `BlendShapeBuffer` (0x200AF) instead: `int == 1`, 11 u32
offsets, shape count, vertex count, int, bone indices count, then a data region. Offsets are
file offsets **minus 64**, and 0 means absent. Positions are at offset 0 and UVs at offset 3,
both 16 bytes per vertex (float3 + pad, float2 + 8 pad). Normals are not stored, so they are
computed.

Result: `--mesh-selftest` on `Spore_Graphics` converts 6,714 meshes (2,422 gmsh + all 7,402
RW4 meshes across 4,292 files) with zero failures. Rendered both a normal and a blend-shape
mesh to confirm shading, not just absence of panics.
