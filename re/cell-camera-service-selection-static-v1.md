This extends [cell-gameplay-camera-static-v1.md](cell-gameplay-camera-static-v1.md) using the installed `D:\Games\SPORE Collection\SporeBin\SporeApp.exe`, SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. Addresses are virtual addresses. This is executable-byte and x86 disassembly evidence, not execution evidence. No native game, UI or GPU code was run.

## Controller selection

The manager obtained through `67D830` owns the service returned by manager vtable +50. Under the constructor/vtable chain established in the earlier note, that service has vtable `01410688`. Its virtual +34 points to `7C6020`: the function searches a structure at service +60 using its input, and, when the lookup finds an entry, forwards the entry's word at +4 to service virtual +54 (`7C5DC0`), returning true. On no match it returns false. The word is an index, not directly the camera-object pointer.

`7C5DC0` checks the new index against the pointer-array span at +80..+84. On the accepted branch it calls the previously selected array object's virtual +1C, stores the new index at service +A8, calls `7C5B80`, then calls the new selected object's virtual +18. `7C5B20` (service virtual +38) reads that index and returns `array[index]`, or null for a negative index. This provides an actionable lookup-to-controller switch path, conditional on that concrete vtable; it does not identify the selected controller's concrete class or its Cell-stage input key.

A separate generic helper at `B5CB80` obtains the service through `67D830` / manager +50, forwards its caller-supplied argument to service +34, then queries the selected service +38 object for interface ID `011966ED` when non-null. It does not embed the selected key. An executable-byte scan for relative `call B5CB80` found calls at `EF1029`, `EF151B`, `EF2344`, and `EFE1E0` in the bounded `E00000..EFFFFF` range, but none in `E50000..E6FFFF`. This scan is only candidate discovery: it does not cover indirect calls, alternate code paths, function ownership, or prove any of the four addresses belongs to Cell. Editor-path code at `579688..5796D4` reads property `300DB745` and forwards its returned word to the same service +34; the prior editor note identifies this as the Cell UI editor property, not gameplay selection.

## Dispatch to the camera object

Service virtual +2C points to `7C5D40`. If service +A8 is nonnegative and service +B0 is non-null, it loads the selected controller from the +80 array and eventually invokes its virtual +20 with the +B0 object and the routine's own argument. It also conditionally calls `7C5B80` after comparing data associated with the controller's virtual +4C result. The earlier note establishes that manager virtual +54 stores its supplied value in manager +30 and forwards it to service +B0; manager virtual +58 returns that +30 value. Thus the dispatch connects a selected controller to the shared camera-like object. The concrete controller implementation, cadence, argument semantics, and its actual transform math are still unknown. Do not infer a frame rate or movement formula from this dispatch alone.

`7C36D0` reads the first three floats from the matrix's four 16-byte groups in order +30, +10, +20, +00 when the corresponding output pointers are non-null. At `E90FA2..E90FCA`, a caller retrieves manager +50 then service +1C (the +B0 pointer) and requests its +30 group through that reader if non-null. `E99AD7..E99B3E` similarly obtains +B0 and requests its +30 and +10 groups. These are independent static examples of consumers of that shared object, not proof of their runtime execution or of an actor-to-camera update.

## Cell stage connection and next boundary

In stage setup `E5D9E0`, manager +50 and +58 results are saved at `E5DA9C..E5DABC`. At `E5DB4A..E5DB68`, `E5DC0D..E5DC2B`, and `E5DE4C..E5DE69`, both saved results are passed as arguments to virtual +84 on three objects returned by `E82760` for indices 2, 1, and 0 respectively. These are associated with the Cell stage's effects-world setup in the earlier note. The calls establish transfer of both service and camera-object values into those objects, subject to successful initialization; their virtual implementations and actual render-time use have not been followed here. This does not prove the auxiliary object `016B5298` is the manager +30 object.

The remaining decisive trace is to identify the caller and input key selecting the service +34 controller in the actual Cell stage, resolve that key against installed overlay resources and the registered concrete class, and trace that class's virtual +20 update and anchor provenance. A runtime capture would still be needed to establish the selected branch, live values, and frame-specific transform. Neither this note nor the auxiliary-camera constants supports claiming a 1:1 gameplay camera.
