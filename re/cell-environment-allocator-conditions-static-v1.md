# Cell environment allocation contents: static conditions

This extends [the construction trace](cell-environment-construction-static-v1.md). The installed `SporeApp.exe` SHA-256 is `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. These are conditional static paths, not observations of a particular allocation or live rebuild. Valid manager structures, calls, ranges and unhooked imports are assumed.

At `E4EB27..E4EB37`, `E4EB20` passes size `30580h`, a tag pointer, and four zero arguments to `F472B0`. Its argument shuffle passes the size and zero as the first two arguments to `928750`, which calls `927940(size=30580h, flags=0)` at `92876B..928774`. `926500` rounds this request to allocator size `30588h`. Zero flags do not select a demonstrated unconditional payload clear.

A conditional reuse path is decisive against a universal fresh-zero inference. For sizes at least `200h`, `927B2F..927B89` walks manager lists and tests chunk size. When a sufficiently large entry is accepted and `[manager+468h]` is zero, `927B65` branches to `927ED9`; `927ED9..927F23` unlinks the entry, handles the remainder and returns the chunk's address plus eight. A remainder smaller than `10h` branches instead to the return at `927E7E..927E8A`. Neither inspected return path contains a payload-wide clear. Its reachability for any specific environment is not established; metadata writes and later writers preclude a blanket claim that every returned byte remains unchanged. This establishes a supported route on which the allocator need not supply an all-zero payload.

A separate route can obtain fresh OS pages. At `927CD5..927D06`, the call to `926C70` depends on manager byte `+46D`, the normalized-size threshold `+494`, and counts `+488/+490`. `926C70` calculates the allocation extent from manager `+4D4`; at `926C8F..926CAE` it calls imported `KERNEL32!VirtualAlloc` (IAT `013CC1C8`) with null address, `PAGE_READWRITE`, and allocation flags `3000h` or `103000h` according to manager byte `+498`. On success it sets allocation metadata and returns the aligned region plus eight at `926D17`. Under documented Windows behavior newly committed pages start zero; `3000h` includes reserve and commit, and `103000h` adds top-down placement. See [VirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc).

For that specific successful fresh-page route, valid alignment and extent, and no aliases or intervening writes, the constructor's untouched `+15F94`, `+1C210` and `+1D4D0` bytes can conditionally be inferred zero initially: the allocator's visible header/tail bookkeeping is outside the requested user extent. That inference also requires the constructor's called functions and any other code not to write those locations before the read. It is not proof of which route was taken, actual manager state, the value at first rebuild, or later live state. The explicit constructor writes and later `E4EA40` ordering remain as described in the construction trace.

Another route through `927020` uses `VirtualAlloc` with a manager-derived address, `MEM_COMMIT` (`1000h`) and `PAGE_READWRITE` at `92707C..92708C`. The prior state of those pages and all manager paths were not established here. Windows permits committing already committed pages, so this call alone does not prove the returned storage was freshly zeroed. Neither this partial path inspection nor the PE image's own initial state establishes the environment's heap contents.
