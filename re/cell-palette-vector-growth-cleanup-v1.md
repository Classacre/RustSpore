# Cell palette vector growth and cleanup: static boundary

This is an offline, conditional source trace, not a native run or an observed draw. SporeApp.exe SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. Selective Ghidra 12.1.4 `-noanalysis` independently disassembled/decompiled `9C68E0` and `FB3680`, reported success and bodies `9C68E0..9C6AA0` and `FB3680..FB36E2`. Its separate project, script, logs and exact Capstone-decoded instruction bytes for these functions and the cleanup callsite are in `target/ghidra-palette-lifetime-v1/`. The manually seeded decompilation has incomplete types and cross-references; it is not REA Evidence. The loader reported import warnings and unresolved library links.

## Growth and shrinking

`9C6B10` receives the vector at CMID +10. Under valid-vector arithmetic, its comparison of requested element count against the current count is unsigned. If growth is needed, `9C68E0` checks the requested insertion count against available capacity using unsigned comparison. Within capacity it can modify existing storage and update the end pointer. On the insufficient-capacity branch `9C69E0..9C6A94`, it computes a new capacity candidate, allocates `48 * capacity`, calls copy/fill helpers, conditionally calls `F47290` for the previous nonnull storage only when the word at old pointer -4 is nonzero, then stores the new begin, end and capacity pointers. Allocation failure, arithmetic wrap, exceptional cleanup and helper behavior are not established by this narrow trace. This branch can replace and conditionally free the prior allocation; a previously published LOD +10 pointer is not stable across it without an additional synchronization/lifetime admission.

On the non-growth branch of `9C6B10`, `FB3680` moves 48-byte rows where needed and updates vector +4; its inspected instruction body does not free the vector allocation. The meaning of all caller-supplied positions and behavior for malformed ranges are not established. The subsequent `9C6E40` reload of CMID vector +10 after the resize is therefore an important dataflow boundary, not a guarantee that an earlier published pointer remains usable.

## Observed cleanup branch

On the failed-initialization branch of `A0B110`, `A0B471..A0B489` passes the nonnull CMID to `A0A010` and then passes the CMID allocation to `F47290`; it clears CID +2C0 afterwards. In `A0A010`, `A0A03B..A0A04E` tests CMID +10 and the word at its pointer minus four; if both are nonzero it passes that vector pointer to `F47290`. It then proceeds to CMID +8 cleanup and release via CMID +4. The inspected routine has no explicit LOD +10 clearing call before the vector-free instruction. This is a conditional failed-initialization route, not proof of teardown order in every live actor, that a previously published LOD existed, or that a dangling read occurs. Other cleanup, GPU completion, thread scheduling and aliasing are not ruled in or out.

## Integration consequence

An opt-in application diagnostic can safely join a **caller-admitted immutable matrix snapshot** to the existing checked direct-draw descriptor resolver and state-4 argument model, retaining that snapshot through a single headless diagnostic draw and rejecting a changed generation before consumption. This is a safety policy for RustSpore rather than a claim that the original used generations or identical lifetime rules. It must label the source data, synthetic or explicitly supplied pose, descriptor and snapshot identity separately. A real animated Jawhead remains gated on establishing actual CMID-to-LOD selection and pose generation, update-to-draw scheduling and GPU completion/lifetime; the static cleanup path alone does not justify injecting a pointer into the visible game. No native process or GUI was run.
On a narrower valid-state thought experiment, an initially empty CMID vector resized by `9C6B10` to ten entries enters `9C68E0`'s insufficient-capacity branch. Its candidate capacity is `max(2*old_count or 1, old_count+insert)`, so old count zero and insert ten request exactly ten 48-byte rows (480 bytes), subject to normal arithmetic and successful allocation. A later growth may replace or free that allocation. If that exact pointer were simultaneously selected for the admitted `(0,36)` zero-start/mode upload, the requested extent would exceed that allocation. This is a conditional compatibility observation, not evidence that the actual source selects that pointer/path, that allocation occurred, or that an overread or crash happened.
