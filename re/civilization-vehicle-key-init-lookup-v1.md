## Constructor and first-key producer boundary

Under the previously traced `B1EAF0` labeled cVehicle allocation and successful `CA7C20` construction, `CA7C20` passes vehicle +34 to `C43940`, which calls base initializer `C89570` on that same embedded interface. At `C896AA..C896B6`, with ECX zero, it writes zero to embedded +90/+94/+98, corresponding to vehicle +C4/+C8/+CC. This records initialization at that point only: later constructor operations, indirect callbacks, loading or reuse can change it, and an initially zero key does not establish a zero key when a view is created.

On the standard admitted vehicle interface table, `AD1FC0` virtual +90 returns whether embedded +90 is nonzero. The previously traced `E94E00` vehicle-view path requires that virtual's AL nonzero before reading the three-word triple via virtual +98. Consequently, if this initialized zero survives to that check without mutation and the admitted standard vtable is still active, that path skips the triple copy. Some intervening key producer must supply a nonzero first word for this route to pass; neither the constructor initializer nor the later view copying its current value identifies that producer.

The known conditional writer `C88750` copies three caller-supplied words to embedded +90/+94/+98 when changed and dispatches virtual +8C. The standard vehicle +94 `CA78A0` reaches it for second words `24682294` or `476A98C7`; the view's `E92810` can itself send a copied triple to +94. The actual first nonzero caller, supplied triple, selected vehicle, callback mutations, save/provider state and lifetime are not determined by these paths. A bounded PE E8-rel32 raw scan found direct call candidates to `C88750` at `BCD1FA`, `C63F65`, `C64DE4`, `C65EDE`, `C6618C`, and `CA78D5`; only the latter was decoded in the previous vehicle-specific trace. Raw matches are not validated function boundaries or proof that the other callers operate on this class, and indirect writers are outside this scan.
