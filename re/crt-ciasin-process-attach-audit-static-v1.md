# `_CIasin` candidate DLL process-attach boundary

This partial static audit supplements [the fixed reference plan](crt-ciasin-fixed-reference-plan-v1.md). The selected local `SporeBin/msvcr90.dll` is x86 PE32, SHA-256 `ed0170d3de86da33e02bfa1605eec8ff6010583481b1c530843867c1939d2185`, preferred base `78520000h`. No DLL or original instruction was executed. All addresses below are preferred VAs; PE relocation and actual loader state are separate.

## Attach operations visible in the DLL

The PE entry is `78542D40`. For reason `1` it calls `7858ECF0` before forwarding its three entry arguments to `78542B94`. `7858ECF0` conditionally reads `GetSystemTimeAsFileTime`, process and thread IDs, `GetTickCount` and `QueryPerformanceCounter`, combines them into a DLL global and writes its complement. These are real conditional host-process/time observations and writes, not evidence of a particular runtime value.

The process-attach branch of `78542B94` calls `785836CF(1)`, `78543A99`, `785865E4`, `78562820`, `78543184`, `785422BC(0)` and `785427E0` under successive success gates; failure follows cleanup paths. The retained `-noanalysis` decompilation has incomplete stack recovery, so signatures and complete reachability are not asserted from pseudocode alone. Selected consequences supported by the code include:

* `785836CF` calls `HeapCreate` and conditionally initializes allocator state; failed initialization can call `HeapDestroy`.
* `78543A99` obtains `KERNEL32.DLL`, asks `GetProcAddress` for `FlsAlloc`, `FlsGetValue`, `FlsSetValue` and `FlsFree`, has a TLS fallback, calls `TlsAlloc`/`TlsSetValue`, and follows further indirect function pointers and allocation/initialization paths. Those pointer identities and results are runtime-dependent.
* `785865E4` obtains process startup information and allocates/initializes CRT I/O bookkeeping, including paths depending on startup-provided data and handles. `78543184` walks an environment-derived string block and allocates the DLL's environment representation. Full effects and error handling were not exhaustively audited here.
* `785422BC` calls `78597336(0)` and then `78542211` over pointer array `78521290..785212A8`. The image words are `0`, `7854EE76`, `785579A3`, `7858CA2D`, `7859A653`, `785A35CA`. These are conditional initializer calls: observed targets include CRT stream allocation, a system-time-based initialization, allocator-backed storage, and the previously documented CPU/OS SSE2 capability and enable checks. A nonzero initializer return stops this sequence. Further initialization/cleanup follows depending on that result.
* `785427E0` examines module/activation context and path state. Its inspected entry asks `GetModuleHandleW` for `kernel32.dll`, obtains `FindActCtxSectionStringW` through `GetProcAddress`, and tests for `PGORT90.dll` and `MSCOREE.dll`; later paths consult module filename, system directories and additional helpers. Complete effects and helper/indirect branches remain open.

The PE import table has one direct descriptor, `KERNEL32.dll` with 161 entries, including `LoadLibraryA`, `LoadLibraryW`, `GetProcAddress`, allocation, TLS and environment-related APIs. A bounded executable-byte scan for direct `FF 15` IAT calls finds `LoadLibraryA` at `7854C15B`, `7858D317`, `7858D610`, `LoadLibraryW` at `785971A0`, and `GetProcAddress` at nine direct sites including `7854281C`. This is an **encoding scan**, not a reachability result or complete dynamic-load census: calls through loaded registers, wrappers, indirect pointers and computed control flow may be omitted. The attach reachability of the listed `LoadLibrary` sites has not been established or disproved. The imported `KERNEL32.dll` may itself involve OS-specific loader forwarding and runtime behavior outside this DLL.

## Decision and remaining gate

There is no demonstrated safe direct-loader boundary yet. Checking `GetModuleFileNameW` and the loaded hash after `LoadLibraryExW` is too late to prevent process-attach execution by an unexpected redirected image. Even if the selected image is admitted stable and exact, the reviewed path includes host-specific heap, TLS/FLS, timing, startup, environment and activation-context operations, and indirect callbacks whose full effects are not closed. The process's loader configuration, `.local`/activation state, loaded module identities and host OS must be controlled or admitted before loading; do not claim that the path flags alone establish them.

The next direct-load gate is a reviewed pre-load identity/redirection boundary plus complete reachability and effect review of the attach success/failure/cleanup paths, initializer targets, resolved pointers and dynamic loading. If that is impractical, the separately described no-DLL, fixed-input legacy-instruction host is the narrower research route; its own code/data/reference allowlist and return policy still require independent analysis. Neither route establishes the game's actual loaded DLL or dispatch choice.
