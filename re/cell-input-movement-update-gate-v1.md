# Cell source input and movement: application integration gate

This is a code/evidence audit, not a new native execution. The current `cell_game.rs::Game` owns `CellWorld`; `drive` calls `world.advance(dt, keyboard_input(...))`. Selecting source artwork changes the inspection mesh, not the actor or controller state. The separate `--source-player` and `--source-sweep-fixture` commands are controlled headless inspections and do not populate that application world. Their derived source fields and synthetic handles cannot be treated as a live player or candidate actor.

The bounded player target bridge is source-backed but has no legitimate current application input. The conditional `E6F620` route reads global state `+C4`, resolves the selected handle through the source actor pool, copies that actor's current `+4C/+50/+54` words to the player target and clears byte `+04`; a failed lookup clears `+C4`. It then obtains the source actor's cache and enters `E6EF30`. The checked pool-to-target fixture models that copy only. The actual `Game_Cell` callback's active registration, event receiver and listener/target routing, camera/viewport and sampled cursor, `E87270` query and filters, source pool, player identity and cache lifetime remain conditional or unknown. The current prototype keyboard axes, Bevy camera and prototype IDs do not supply these values.

Even an admitted source selection would not finish movement. Existing isolated kernels model useful parts, including axial target projection, sampled flow, selected AI/cache getters, size scaling, swimming deltas and the bounded `E55FB0` accumulator application. The complete `E6EF30` branch still needs the source flow and runtime-data providers, selection and ordering of these inputs, state/turn helpers, x87/MXCSR policy and actual actor/environment accumulator ownership. The source runtime-data notes identify `E56440`'s `data1` consumer and `E563F0`'s state-dependent `data2` path; identifying a consumer does not establish the active actor's sampled producer or bind it to the Cell world. Applying a selected isolated kernel to prototype position/velocity would invent the missing movement route.

The next application integration should start with a separately selected source state, not a flag on the art path: admit a generation-checked source actor pool and separately established player, creation/definition fixups and provider/cache identities; then admit the source query's candidate actor set, selection/camera state and ordered event route. Keep the stage explicitly unsupported until it can obtain the live values required for target and movement. A headless integration test can inject labeled controlled state and verify resolution, stale-handle rejection and update order, but passing it establishes the supplied handoff only. Genuine source-backed interaction additionally needs actual actor construction/assignment, provider and leaf lifecycle, cursor/camera event delivery, and an admitted movement continuation. The current code cannot provide those inputs, so no source movement is wired into `drive` by this audit.
