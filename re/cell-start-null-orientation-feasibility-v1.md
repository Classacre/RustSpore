# Cell null-orientation: implementation and validation boundary

This is a static feasibility review of `re/cell-start-null-orientation-static-v1.md`, `crates/spore-core/src/native_x87.rs`, `native_sse.rs`, `cell_request_rng_v1.rs`, and the guarded fixture described in `re/anim-quaternion-native.md`. No Cargo, GPU, host-native fixture or original game was executed for this review. It does not establish the retail processor, floating-point environment, random state, globals, or runtime branch selection.

## Feasible bounded implementation

For the source branch where definition byte `+AC != 1` and orientation pointer is null, start from an explicitly supplied post-size RNG state only after admitting successful intervening allocation. `cell_request_rng_v1::Rng` models the next draw for nonzero state under PC53/PC64; `Fraction::as_f64()` is an exact numeric representation of the fraction, and `Extended::from_f64` retains it. Reject zero fraction because the helper loses the source's possible signed zero; reject zero seed, reserved precision, unmasked exceptions, nonfinite inputs and unsupported results. Neither an admitted state nor a synthetic allocation proves a real actor was created.

Use x87 `Context::mul` in source order, first fraction times the explicitly supplied binary32 angle global, then times binary32 0.5. Preserve that 80-bit angle for both operations. For the observed initializer bits `40C90FDB` and admitted positive nonzero fractions strictly below 1, this angle is positive and below 4 under the admitted PC53/PC64 rounding modes; the observed initial global is not proof of its runtime value. Restrict arbitrary supplied globals by checking the computed absolute angle against 4 before the transcendental operations, rather than assuming this initializer is unchanged.

`Context::sin_magnitude_at_most_four` performs host `FSIN`, checks C2 immediately, returns retained 80-bit storage and restores the x87 environment; `Context::store_f32` performs the separate RC-controlled binary32 commit. Both are x86/x86_64 hardware-dependent. The existing code has **no FCOS helper**. A similarly bounded host FCOS helper is a necessary addition: operate on the original retained angle, inspect C2 immediately, reject incomplete reduction and nonfinite output, preserve the same environment/stack obligations, then commit to binary32 with the selected RC. Capturing and restoring between operations does not reproduce native sticky flags, which this model must exclude. A future review should specifically assess environment/tag handling, empty-stack assumptions, exception masking, architecture fallback, and zero/sign behavior; a software `cos` is not a substitute.

The sine binary32 store precedes the three separate SSE `MULSS` operations on the supplied axis words; the cosine uses the unrounded retained angle and supplies the fourth word. `native_sse::scoped` currently offers only MXCSR `1F80` (nearest, gradual underflow, DAZ off, masked exceptions), saving and restoring the incoming full MXCSR on the same thread. That is a viable explicit fixture policy, not evidence of the original thread's state. Preserve individual instruction order and signed zero; finite-only admission and rejection policies must be specified independently from native exceptional behavior. The nine matrix outputs need an instruction-by-instruction `59C000` implementation, not merely the algebraic formulas in the existing note; separately checked operations must not be reassociated or contracted. Position and +48/+4A updates and allocation remain separate boundaries.

## Validation that could establish host-specific agreement

The existing animation quaternion fixture provides a precedent, not direct validation of this Cell branch. Its reviewed design copies pinned original instruction bytes and readonly constants into guarded regions, fills unlisted code with INT3, audits memory operands, control flow and imports, and verifies stack/control state and canaries; the referenced note documents its separate measured execution. For this branch, first statically identify exact bounded byte spans, relocations, all data dependencies, and function boundaries. A new dedicated x86 host would need exact source instruction bytes and constant identities, a small explicit RNG fixture or separately verified original RNG span, and bounded writable scratch with guards. Do not jump into the complete constructor with fabricated pointers or omit calls while claiming full constructor execution. An independently reviewed isolated slice may instead start with an explicitly supplied retained angle and axis; a second fixture can include the admitted RNG and ordered angle operations once its dependencies are audited. Pin executable and each copied span, fixture generator and outputs, validate branch targets and memory accesses, and use a separate process with timeout and strict output bounds.

Under explicit masked x87 CW and MXCSR, record the retained angle, status/C2 immediately after each transcendental, sine and cosine f32 words, axis products and ordered matrix words. Check x87 stack balance, control restoration, SSE controls and scratch canaries, use scratch poisoning, and test boundary angles, rounding modes, signed-zero policy, candidate initializer, branch skips and rejection cases. Compare exact bits with the implementation on the **same processor and explicit environment**, identify CPU and OS, and report independently checked raw inputs and replies. Distinguish a source-byte execution from a hand-reassembled fixture and a rational arithmetic model; only the former exercises the copied source instruction stream, and neither authenticates the retail live environment or behavior on another CPU. A reference using host FSIN/FCOS and a Rust helper using the same instructions provides host-specific conformance, not an independent mathematical or cross-processor oracle.

Exact control and rounding can therefore be *specified and measured in a future guarded host fixture*, and host-specific output bits compared without substituting approximate library trig. They cannot be established as the original game's actual control state or universal cross-processor output by the existing static trace. The current repository does not yet supply FCOS or a Cell-specific guarded fixture, so full bit-exact null-orientation conformance is presently unverified.
