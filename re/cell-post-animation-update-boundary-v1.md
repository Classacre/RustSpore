# Cell post-animation update boundary

Static source only, executable SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. `E806E0` calls `E53960` and then `E5FEE0` followed by `E6CA50` on one branch as documented in `cell-world-scheduler-palette-update-v1.md`; this does not by itself identify GPU submission or establish live dispatch.

A separate Ghidra 12.1.4 `-noanalysis` import manually seeded `E5FEE0` and `E6CA50`; it reports decompiler completion and exit 0. The project, logs and PE-mapped Capstone bytes are retained in `target/ghidra-cell-post-update-v1/`. This is not REA Evidence or runtime execution. Ghidra reported disjoint bodies `E5FEE0..E60913` and `E60C66..E60DF9`, and for `E6CA50` also unexpected detached ranges `005FD9E0..005FDA07` and `005FDAD9..005FDADB`. Direct bytes establish a connection to the first range: `E6CB17` calls `67C620`, `E6CB1C` moves its return to ECX, `E6CB1E` tears down the local stack, and `E6CB21` jumps to `005FD9E0`. The tail target calls `804DA0`, updates the receiver +2C, and dispatches on receiver +24: an unsigned +24 value above 3 (including negative signed bit patterns) branches to `005FDAD9`, while 0..3 jump through the table at `005FDADC`. That establishes a conditional control-flow connection, not the target function identity or its overall semantics. The reported `005FDAD9..005FDADB` range is the out-of-range branch exit. The image table contains case targets `005FDA08`, `005FDA30`, `005FDA64` and `005FDAAF`; bounded byte decoding shows conditional changes to receiver +24 and calls including `5FD740`, `5FD8D0`, `8102F0` and `810310`, Cases 2 and 3 increment receiver +28 before `COMISS`/`JBE`; unordered comparisons take the exit branch only when the comparison completes, and the floating-point exception state is not admitted here. The meanings of these cases and helper effects, the receiver identity and the surrounding function identity remain unresolved. Neither body, full callees nor decompiled signatures should be treated as complete without further corroboration. Exact tail bytes are retained in `target/ghidra-cell-post-update-v1/tail-instructions.txt`.

The existing independently decoded trace `cell-cursor-ray-producer-static-v1.md` identifies a concrete conditional camera update inside `E5FEE0`: `E60D03..E60D0F` obtains the camera from manager +58, `10436F0` constructs a matrix, and `E60DAA..E60DE6` configures it through `7C4540`, `7C4560`, `7C4CD0`, `7C45E0`; it then calls `E54890`, a separate auxiliary-camera path. This is a camera-state update under the documented actor, manager and guard admissions, not proof of shader submission, draw completion or the current visible frame. Previous source trace documents the separate `E54890` camera and exact arithmetic in `cell-aux-camera-transform-static-v1.md`. In particular the two camera objects are not established equal.

This investigation does not establish that either post-update call dispatches `73FD30` or that its draw follows the animation palette update within a source frame. The tail-connected `E6CA50` path has unresolved jump-table case semantics and indirect calls, and its selective decompiler output cannot close that gap. Next, locate the actual scheduler-to-render submission through authenticated function boundaries, vtable identities and callsites, then establish same-object identity and synchronization with the animation-world update; avoid adopting a headless diagnostic's own update/draw sequence as evidence of native cadence.
