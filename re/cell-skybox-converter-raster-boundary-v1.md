# Cell skybox B-to-C candidate: raster selection boundary

This is a read-only follow-up to [the fallback boundary](cell-skybox-texture-fallback-boundary-v1.md). It does not establish that a Cell runtime requested, selected, converted or rendered this resource. The base executable is SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`.

At `76A10E..76A143`, the conversion branch requires requested type `2F4E681C` and the supplied source descriptor's type `2F4E681B`. It passes descriptor-derived values to `7653C0`, which queries the manager obtained by `67D7F0` and, on its successful branch, calls `764BC0`. `764BC0` acquires a further object via virtual +14, obtains its +18 value, calls `11E2150`, and iterates entries via `11E26D0`. It tests each returned tag against `00020003`; the first matching tag takes the `764CD7` path. A zero extracted payload returns failure rather than proving that a later entry is used. On the nonzero path it stores the extracted word at output +18 and retains the acquired object at +1C with reference-count operations. This is a conditional object and value selection trace, not proof that the object is a usable GPU texture, that the manager reload succeeds, or that the iteration corresponds one-to-one with serialized RW4 section order. The relevant hash-bound source bytes and instructions are in `target/source-cell/skybox-btype-converter-static-20261108-v1.json`, SHA-256 `ffd2b11064710b5e2411bbda95495d75df1398631de56446b9f1ed91e5b7e8f1`.

A fresh explicit exact-key read of `Data/Spore_Graphics.package` found one `BD08BD8A:2F4E681B:00000000` entry. Its decoded payload SHA-256 was `5705df1ab03e94c58c8a890383026e68c68dfe64ba488d4d767f2706d8ad8aec`. The independent container framing validator returned `ok`; its section table has two entries and **one** `00020003` Raster section, at ordinal 1. The package SHA-256 was `e01bb86d8ddf02c56d52394b4e1db7181c1e1ebe1878bf6fb72c4ee523fcedd1` both before and after. The report `target/source-cell/skybox-btype-raster-census-20261108-v1.json` has SHA-256 `b07bd5e2c3c7cbb1a0875b1f2e23ac11e4dd3521c6ef2864b583e74a3765e2ef`. The package reader reopens the path; before/after equality does not rule out transient replacement. Container uniqueness narrows the earlier first-raster ambiguity for this explicit payload, but it does not establish what `11E2150`/`11E26D0` expose after native loading, whether the payload is non-null there, or any runtime winner.

The next testable boundary is to trace and validate `11E2150` and `11E26D0` for this loaded RW4 object's collection: establish object ownership, the mapping of serialized ordinal/type to returned tag/payload, and lifetime across `764BC0`. A controlled, hash-bound source fixture can then compare that enumeration and chosen raster to an isolated original-instruction host with admitted provider objects and explicit return values; it must not infer that a live provider or device used the fixture. Separately the native database set/order, earlier cache hits and type-map mutation remain unresolved.

A further bounded decode narrows that enumeration. `11E2150` returns receiver +24; `11E26D0` rejects an index at or above that count and reads a 24-byte record at receiver +30 plus `24*index`. It uses the record's +14 word as a key to `11EAE90`, a linear search of 20-byte registry records, and writes the first word of the found record as the returned tag; a missing registry result yields zero. It also calls `11EB390` and `11EB580` to construct other returned fields. Registry acquisition goes through the initialized callback at `140A51C`, `11E3C60`, and an indirect vtable call. Thus the static converter's `20003` tag is registry-derived; a matching serialized section type alone is not proof of that returned tag. The record stride and the candidate's two section rows suggest a testable relationship, but their identity and post-load mutation are not yet established. Hash-bound bounded listings are `target/source-cell/skybox-btype-enumerator-static-20261108-v1.json`, SHA-256 `d34fcb4a5c70025ab2bda89c12c05a02fb684999789f1d3523d9d267800f022d`. The sharper next step is to trace the RW4 loader populating receiver +24/+30 and the registry's `20003` registration, then compare the actual returned tag and nonzero payload on an admitted, stable source-object fixture.

## Conditional loader and registry join

On the inspected `764350` path, `7643A6` calls `11E3A60` with a supplied image pointer. When that image's +38 old-base word differs from its present address, `11E3ACB..11E3AD7` rebases the +30 table pointer by `present - old_base`, then the loop at `11E3AE0..11E3BA4` visits +24 records at 24-byte stride. For each record it copies the original first word to +4. For types outside `10030..1003F`, it then rebases the first word by the same `present - old_base`; special base-resource records use a different branch. These statements are conditional on valid, loaded contiguous image memory and this particular relocation branch; they do not prove that every provider or live loader calls it successfully.

The explicit hash-checked skybox B payload has image +24 `2`, +30 `144h`, +38 `0`; record 1 is `[124h, 0, 20h, 4, 5, 20003h]`. If those source bytes are loaded unchanged at a valid nonzero image address and this relocation completes without later record mutation, the table becomes `image+144h`, and that record's first word becomes `image+124h` while its +4 retains `124h`. `11E26D0` would then expose that first word as the result's +4 payload pointer, subject to the separate registry and helper calls. A fresh source-bound projection of those raw words is `target/source-cell/skybox-btype-source-relocation-20261108-v1.json`, SHA-256 `65c9d6769b50c090fcc2d4ddeb6e7a69c53a1b3b1e60937c639783b4185691f7`. This is relocation algebra on source bytes, not native execution or a claim that the pointer is a ready GPU texture.

The conditional registration is now also narrower: graphics startup `763F90` calls `11E2070` with `20003h`. `11E2070` searches the same 20-byte registry via `11EAE90` and, when absent, calls `11EAF00`; the latter stores its argument as the new record's first word. Therefore, if registration completes on the same unchanged registry and enumeration's record +14 remains `20003h`, `11E26D0`'s registry lookup returns tag `20003h`. The same startup writes hook `763BC0` at registry record +0C; separate graphics setup `11F0600` also obtains the `20003h` record and writes `11F04A0` at +0C. These can overwrite one another, so execution order matters. The `763BC0` hook may either call `11F04A0` or take a branch that writes zero to its object's +8 and returns success. `11F04A0` resolves the Raster's +1C reference through `11E20B0` and has additional failure and device-related paths. Thus a nonzero rebased Raster *object pointer* does not establish a nonzero loaded texture/device pointer.

The bounded loader/registration listings are `target/source-cell/skybox-rw4-relocation-registry-static-20261108-v1.json`, SHA-256 `28f6ef660d6c8b7c21c3f3d0dda1a950c826688c8b457e5e517148c999cc6cdc`. The next focused test is a controlled loader/registry fixture with pinned B bytes, valid relocation storage, explicit registry initialization/hook order and a captured result tag/object offset, followed separately by a checked hook/device outcome. Provider precedence, cache hits, active effect, runtime material and camera remain unresolved throughout.

## Conditional Raster hook and device path

The explicit candidate's 32-byte Raster has format `DXT5`, flags word `00000008`, width and height 256, mip count 9, and +1C reference word zero. Given those words remain unchanged and the `11F04A0` hook is actually selected, `11E20B0` must resolve the +1C reference to a nonzero source pointer. `11EF940` selects its jump-table index 7, `11EFA82`; the candidate's flag bits select the two-dimensional device path at `11EFB9E`. On the traced standard D3D9 device association, slot +5C is `CreateTexture`: its arguments are width 256, height 256, 9 levels, usage zero, DXT5 format, pool 1, output pointer at Raster +8 and a null shared handle. A negative HRESULT takes the failure exit. A valid device and successful call with a usable non-null output remain admissions, not observed source state.

On the candidate's unchanged flags, `11F04A0` next iterates nine mip levels. `11F0050` calls `11EF530`, whose relevant texture branch invokes vtable +4C (D3D9 texture `LockRect` under the standard interface association); the DXT5 branch copies the number of bytes returned by `11EFDE0`, then calls `11EF660`, whose relevant branch invokes +50 (`UnlockRect`). Crucially, `11F0050` does **not** test `11EF660`'s return before returning success, so outer success alone does not prove a successful unlock or usable output. The source pointer, source buffer extents, resource lifetime, device behavior and all nine lock/copy operations must be valid. The other registered hook `763BC0` can instead take its matching-list branch, write zero at Raster +8 and return success without calling this path.

The read-only source-bound audit `tools/cell_skybox_raster_hook_audit_v1.py` checked the candidate hash and framing, its type-8 jump-table target, and the source DXT5 block-size arithmetic: `[65536, 16384, 4096, 1024, 256, 64, 16, 16, 16]`, totaling the 87,408-byte BaseResource. ## Isolated hook-gate comparison

A separately reviewed hidden x86 host executed copied `763BC0..763C17` with its global pointer redirected to guarded synthetic state and its call to `11F04A0` redirected to an explicit recording stub. All six fixed cases matched the independent expected records: a matching Raster in the first or second list position bypassed the stub, zeroed Raster +8 and returned 1; no match forwarded once; a clear global flag forwarded the stub's return 0; and zero or negative signed count forwarded once. Forwarded calls supplied the expected synthetic Raster and context pointers. Guard and unchanged-memory checks passed, the host exited zero, and stderr was empty. This validates only those six isolated gate cases; the real forwarded hook, callbacks, device, texture, provider and live state were not executed.
