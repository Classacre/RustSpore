# Controlled Creature source frame overlay

`--experimental --creature-game` accepts the optional group `--source-ui-layout <package> --source-ui-atlas <package> --source-ui-fixture <JSON>`, only with `--offscreen --shot <new PNG>`. It selects the explicitly hash-bound `5ED10964:250FE9A2:40464200` layout and `FE081DAA:2F7D0004:31A44893` atlas, validates the serialized 963 -> 886 -> 885 reference, selected slot and source ImageRegion, and emits the mode-2 slices. The fixture supplies layout and atlas SHA-256, `viewport`, `clip`, `destination`, `state` and `resolved_mask`; viewport must be `[0,0,1280,800]`, clip must be within viewport and fully contain destination. This is a safety admission, not source partial-clip behavior. The offscreen target uses that extent and UiScale 1.0; onscreen and resize/DPI scenarios are rejected. Each quad uses Bevy's image rendering and linear sampling; source D3D blend, color, filtering, pixel centers, equal-z ordering and seams are not established as equivalent.

A fixture example under ignored `target/creature-frame-fixture-v1.json` is a controlled placement, not a recovered runtime layout. The atlas and layout bytes are hash checked, while package readers reopen paths and require stable, trusted files. The overlay is one selected authored frame; it does not render the dynamic minimap, establish provider winner or implement a full original HUD, live placement, event state or Creature gameplay. The stage's prototype scene and HUD remain visible underneath it.

A reproducible nonproprietary fixture for the PatchData layout and Spore_Graphics atlas is:

A controlled hidden Vulkan offscreen run using this fixture produced `target/creature-frame-overlay-v1.png` SHA-256 `dd4fd4f4fc0e98729475cbb901d1617d628d7c30e6b2f277a3d4a0d7b035568f`; the image shows a source atlas frame at the supplied position over the prototype target panel. Its baseline `target/creature-frame-base-v1.png` SHA-256 `d2762334adae4fc2d5dcece78d1326c4bdf419859003e7217ebdda56a906fe08` differs at 33,952 pixels, including 17,058 outside a one-pixel-expanded destination. Thus these two separately rendered frames do not prove effects are confined to the destination or establish pixel equivalence. The run reports RTX 3060 Laptop GPU and tick 60; native placement, blending, sampling, ordering and retail HUD appearance remain unverified. Capture logs are retained beside the PNGs.

In the v1 capture the frame overlaps and partially obscures the prototype target-panel text. That visible overlap is a consequence of the supplied fixture placement, not an original layout. The v1 capture predates the later on-screen controlled-overlay notice; it does not validate that notice.

## Conditional frame-local layout

Both hash-bound candidate layouts serialize root 969 `[25,25,825,625]`, child 968 `[7,40,33,65]`, child 966 `[-7,-242,315,-55]`, and frame 963 `[-2,-174,240,-24]`. Parent 968 references SimpleLayout 879 (flags 06) and procedure 880 (class `CF2B2AD4`), whose full runtime behavior and ordering are not established here. Frame 963 references SimpleLayout 887 (flags 06). On a caller-admitted resolved parent-966 rectangle and identity-plus-translation screen mapping, the optional fixture path verifies those parent-child links and 963's procedure, applies the existing native local layout/clamp/floor model, then adds the explicitly supplied screen origin. It rejects overflow, degenerate rectangles, incompatible fixture modes and partial clip. It does not compute parent 966 from the serialized ancestors, characterize proc 880, reconstruct the actual screen transform, or claim native placement.

Use these fields in place of `destination` in the JSON example above:

```json
"parent_966":[0,0,322,187], "screen_origin_966":[100,200], "admit_identity_translation":true
```

Under those supplied inputs the frame rectangle resolves to `[98,213,340,363]`. This is a controlled layout calculation, not an observed runtime rectangle. The earlier arbitrary `destination` fixture remains supported.

`parent_966` is a caller-supplied local parent rectangle; this source helper uses its width and height, not its origin. `screen_origin_966` is the separately admitted screen-space mapping of local `(0,0)` under identity translation. The local mode assumes ordinary round-to-nearest binary32 arithmetic. The caller must not treat these fields as captured source coordinates.

## Root and parent 968 sizing boundary

The source `E032A0` initialization reached from the Creature candidate passes literal UI-world key `2EDD95CA` to `811E30` at `E03352..E0335A`; the already traced shared UI manager route conditionally finds `UIWorld_GlobalUI`, creates/sizes it from its manager parent, attaches loaded layout roots and applies `811090` to the root identified by `FFFFFFFF`. Both candidate 969 roots have that ID. Under successful queue delivery, parent lookup and root attachment, absent later mutation, `811090` replaces the serialized root area with the current external parent spans and moves it to zero. The source descriptor-provider values and event timing remain runtime inputs; a 1280x800 capture target does not prove the same source UI parent dimensions.

The serialized 969 -> 968 link and 968 -> 966 link occur in both pinned layouts. Window 968's local authored rectangle is `[7,40,33,65]`; proc 879 is `2F418D72` with flags `06`, and proc 880 is the separate GlideEffect. If an explicitly admitted root parent has finite nonnegative height H with finite binary32 intermediates, the 879 SimpleLayout helper alone yields local `[7, 40+H, 33, 65+H]`, followed by its wrapper's inverted-edge clamp and layout dispatch floor. This statement is about that helper's local rectangle, not a final screen location, visibility or paint. Source SimpleLayout does not add the parent origin. With a hypothetical H=800, the helper's local output is `[7,840,33,865]`; no inference about on-screen placement follows. The later GlideEffect callback can mutate a separate transform helper and its timing, target and runtime state are unresolved; see `creature-spui-glide-effect-boundary-v1.md`.

Window 966 has authored `[-7,-242,315,-55]` and no serialized `EEC1B00C` procedure property in the selected payloads. That omission does not prove no constructor/default procedure, later attachment, mutation or layout event. Even a caller admission of unchanged 966 local values does not establish the mapping from this local frame to screen, nor the 968-to-966 dispatch order or runtime matrices. Therefore source viewport alone cannot yet determine the `parent_966` and `screen_origin_966` required by the current bounded overlay. The next relevant source trace is Window deserialization/default procedure construction and layout dispatch for 968/966, and the draw transform receiver receiving `95E9B0`'s GlideEffect mutations. No change to placement or default HUD was made here.

## Parent 966 constructor and layout-event follow-up

Direct instruction decoding of the same SHA-256-pinned PE refines the default-list boundary. The Window factory `956E10` allocates `20Ch` bytes and calls `9629F0`. In that constructor `962A65..962A6A` initializes the linked-list head at object +64 to self in both directions; `962A6D..962A7C` zeros +74/+78/+7C/+80, and `962A82..962ABA` zeros rectangles +88..+A4. The constructor then calls `95E8C0` on object +C4 and copies its 17 words to +108, +14C and +190 at `962B60..962B90`. This is an initially empty list and initialized transform-related storage on this constructor path, not proof that the list or matrices remain unchanged at layout or draw time. Allocation success, later initialization and lifetime remain admissions.

Metadata initializer `1300537..130056B` assigns property `EEC1B00C` type word `8013`, target offset `64h`, count 1, and handler descriptor `14417E4`. The separately inspected callback at `961E10` first calls `961A90`, then walks supplied references in reverse and queries interface `2F009DD0`; for each successful interface it invokes Window interface virtual +104 at `961E33..961E5A`. `961A90` traverses the +64 list and invokes/removes entries with observable callbacks; it is not a no-op. The graph shows no serialized `EEC1B00C` on 966, but neither absence of that property nor constructor initialization excludes later registrations, constructor hooks in derived objects, target-window behavior or callbacks. The descriptor-to-callback mapping was subsequently narrowed below; full deserializer reachability remains unproven, particularly for an absent property.

At `95A0F0`, source copies object authored fields +98/+9C/+A0/+A4 into working +88/+8C/+90/+94, dispatches event `10h` via `959750`, then floors all four working values (`95A0FA..95A1A9`). The `958A30` listener dispatcher traverses the +64 list, tests each event mask and can stop when a listener returns nonzero (`958A3D..958AB9`). An initially empty list therefore narrows an admitted no-registration local path, but it does not settle the subsequent target dispatch, whether the event reaches this Window, or modifications through other receivers. Under the stronger explicit admission that no reached callback alters working +88..+94, the integral serialized 966 rectangle remains `[-7,-242,315,-55]` after that local copy/floor; this is an admitted computational result, not a recovered screen placement.

In `9615B0`, the initialized object +C4 17-word block is copied to +108 and `95F740` is called before subsequent owner-dependent virtual operations; the owner-nonnull branch reaches manager calls `9581F0`, `9589D0`, `958220` and virtual +94. Their transform/ownership and callbacks are not resolved by the initial copy. Combined with unresolved GlideEffect dispatch/receiver mutation and root/child translation, the viewport alone cannot bind the frame to a screen rectangle. No new automatic placement is admitted by these observations.

A follow-up byte check fixes the provenance of the constructor's zeros: `9629F0` saves EBX and `9629F1` executes `xor ebx,ebx`. Between that instruction and the stores at `962A5F` and `962A6D..962A7C`, the only calls are `9511C0` and `925C70`. Direct decoding shows the first is a global load followed by `ret`, and the second only initializes its supplied object using EAX/ECX/EDX and returns; neither writes EBX or calls another routine. Thus, on normal return with valid nonaliasing memory, the stores write zero to +70 and +74/+78/+7C/+80/+84 without relying solely on an unexamined callee-save assumption. `962A5C` separately zeroes XMM0 before the rectangle stores. This does not establish post-construction values or protect against aliasing/faults.

The metadata immediate writes and the `958A30` list traversal/mask/early-stop sequence were also rechecked from the same hash-matched PE. In particular, the metadata writes descriptor pointer `14417E4`; it does not by itself prove that the separate `961E10` callback is the invoked implementation for a particular deserialized 966 object. The event dispatcher calls a virtual entry before beginning list traversal, so even a constructor-empty list alone is insufficient to rule out earlier callback effects.

## Property registration and update callbacks

The earlier descriptor-to-handler uncertainty is narrowed by the PE's initialized words. Metadata initializer writes `01441774` at `01550074`, immediately before the property ID at `01550078`; the dword at `01441774` is `00961E10` and the next dword is `00961730`. It separately writes `014417E4` at `0155008C`, whose first three words are `00962BB0`, `00962C40`, `00962CA0`. Thus the two descriptor pointers have distinct roles in the property metadata; the first identifies the read/registration callback candidate and the second is an array-oriented descriptor. This static metadata association does not prove that a particular loader invokes it for an absent property, or that no other code registers a listener.

On the base Window constructor path, interface pointer object +4 uses vtable `01415638`; its virtual +104 entry is `00961FB0`. Under that vtable and successful interface query, the `961E10` reverse-reference callback can therefore reach `961FB0`. The latter calls the supplied listener's virtual +10 for priority, avoids duplicate pointer insertion, calls listener +00 and +14, allocates and links a 16-byte node containing listener and mask into the Window list (interface +60, equivalent to object +64), then sends listener event `1000h`; when Window owner/interface +30 is nonzero it additionally sends event `11h` (`961FB0..9620C2`). Allocation, callback behavior, concurrent mutation and failure are not bounded here. Priority ordering is observable but cannot be reduced to serialized order without the actual callback values. This is a stronger conditional registration chain, not evidence that 966 had an active listener at draw time.

For the same Window interface vtable, +94 is `960AC0`, which when its +30 owner is nonzero calls `95A0F0` followed by `9589D0` and `9581F0` (`960AC7..960B21`); +90 is `9601D0`, which conditionally calls `958930` based on flags and owner. The +94 path also compares old and new rectangle spans after those calls. This associates a conditional owner-backed update with local layout and later owner operations, but does not establish scheduling, unchanged parent/child state, the dynamic `9589D0`/`9581F0` outcomes or a final screen transform. Consequently the current explicit parent rectangle and translation remain necessary; neither the empty constructor list nor omission of serialized property `EEC1B00C` proves a live no-listener state.

### Conditional descendant relayout

A fresh hash check and instruction decode sharpen the +94 update. With a nonzero owner, `960AC0` saves the four pre-call working rectangle words, calls `95A0F0`, `9589D0`, then `9581F0`, and compares old and newly read widths. If they compare equal and ordered, it similarly compares old and new heights; equal and ordered on both skips the `958930`/child loop. A changed or unordered width or height reaches `958930` and iterates the Window's child list at object +3C. For each child, it calls child interface virtual +94 only when child flags have word +2C bit `800h` set or byte +31 bit `02h` set (`960B26..960BAF`). These are source floating-point comparisons under the caller's environment; callbacks between saved and new reads may mutate state. A child pointer and list lifetime, the precise flags after loading, callback order and completion, and the branch when the owner is null remain separate inputs. This explains why a root or parent change alone does not establish a particular descendant layout without the flags and dispatch route.

The metadata initializer recheck confirms `130052D` stores `01441774` immediately before `1300537` writes property `EEC1B00C`; the `8013` type, `64h` offset and separate `014417E4` array descriptor follow. The descriptor's first word is `961E10`. This corroborates the metadata association, not runtime property application or source ownership.

The separate `spui_layout_propagation_v1` model implements only the finite, caller-supplied span comparison and one freshly supplied child flag decision from this branch. It stops at a relayout decision before `958930`, and does not iterate or retain child pointers: the caller must run/admit the external operation and refresh the head, current child, next node and flags after each reached callback. The checked policy rejects nonfinite reached values rather than imitating native unordered relayout, and its scoped MXCSR does not reproduce source sticky status. It is not wired to the Creature fixture or an actual UI world; model results do not establish runtime flags or callback outcomes.

## Window invalidation and transform refresh

Raw source decoding shows the three manager operations called by Window +94 are not themselves matrix multiplications. With a valid supplied object, `9589D0` first skips when object private byte +30 already has bit `20h`; otherwise, under the observed +78/+24 and manager +25 gates, it may link object +20 into the manager's +18 list, sets byte +30 bit `20h`, then walks object +38 links and sets bit `80h` until it sees an already-set bit or null. `9581F0` conditionally links object +20 into manager +18 when object +24 and manager +25 are zero. `958930` checks object byte +30 mask `14h`; if neither bit is set it sets `10h`, then either calls `958220` when object +78 is zero or links object +10 into manager +08. Those linked-list accesses, private state, ownership, prior insertion and mutation are required inputs; none of these methods alone supplies a screen matrix.

A conditional downstream route is visible: `95B420`, on nonzero manager +04, calls `95A250` on that root with two zero arguments at `95B449..95B456`. Within `95A250`, object +30 bit `20h` gates its reset, an identity initialization of object +C4, and message 21 dispatch; callbacks can mutate that message and transform before the result is copied to +108 and passed to `95F740`. In the changed branch, it copies +C4 to +14C, applies a translation derived from the working rectangle midpoint, and if linked parent object +38 is nonzero and its +1E8 is zero, calls `95F980` with the parent's +14C (`95A2D3..95A351`). Another branch copies parent +190 into child +190, applies a negative midpoint, then composes child +108 unless child +148 kind equals 4 (`95A356..95A429`). `95A5BE..95A608` recurses over child-list +3C when either local changed byte is set or object private +30 bit `80h` was set, after clearing that bit. This connects invalidation to conditional transform refresh and parent/child propagation, but not to a particular selected Window identity, a complete frame's final draw transform, or observed runtime state. All matrix storage/aliases, event receivers, effect callbacks, list consistency, FP policy and scheduling must be admitted.

Both decoded candidate SPUI copies contain `EEC1B000` raw flag words root 969 `03h`, 968 `1Bh`, 966 `413h`, and frame 963 `13h`. The separate title trace establishes that this property writes authored Window +2C on its ordinary loading path. Under that same admitted path, 966's `413h` does not contain the +2C `800h` tested by `960B8E`; the other tested input is private byte +31 bit `02h`, which is not determined by that raw flag word. Later property application, events and other code may change either input. These observations do not prove that the conditional child layout call runs or is skipped in a real Creature frame.

## Final transform-to-draw boundary

The `95A250` transform inputs are not derivable from the selected SPUI bytes alone. On the changed path, source forms the working-rectangle midpoint as separate `ADDSS` then `MULSS 0.5` operations, translates a copy of the callback-mutable +C4 block through `95E9B0`, and composes with the admitted parent's +14C only if its +38 link is nonzero and parent +1E8 is zero. For object +190, a linked parent supplies its +190 block and the negative midpoint is applied before optional +108 composition; the no-parent path instead constructs a scale/translation block with `95E930`. `95F980`'s kind and finite arithmetic, any callback edits, transform aliasing, owner links, +1E8 state and the source FP environment all affect the result. A selected layout's authored rectangle and class IDs do not identify these live words.

The previously unjoined `95B57E..95B58C` copy has a more precise conditional producer: in manager update `95B420`'s incremental-list branch, `95B4D0..95B4E4` derives the Window object from the manager's +08 linked node; `95B4FA..95B524` clears its private +30 bit `10h`, prepares a record and calls `95A620` with that Window; `95A620` dispatches message `0Dh` through `959750` before returning. `95B57E` then copies 17 words from that same Window object's +14C into the prepared record +48. The virtual call at `95B569..95B56C` and the message callback can mutate referenced state before this copy, and full allocation, list and pointer validity are admissions. The Window's +14C is therefore a conditional input to a later manager record, but record scheduling, downstream consumption and the selected candidate's live Window identity are still unresolved. Do not treat the record as a demonstrated presented draw or equate its matrix with a Bevy transform.

The smallest useful next source-backed implementation is a bounded transform stage with explicit post-message +C4 and +108 matrices, resolved parent +14C/+190 and +1E8, working rectangle, finite MXCSR policy, and distinct owner/nonalias admissions. It could calculate the source operations for admitted matrix kinds, but would be a controlled producer unless joined to actual property initialization, callbacks, Window graph and renderer record lifetime. The existing overlay's caller-supplied translation remains the honest boundary; no source-to-screen placement can yet be inferred from the packaged layout and viewport alone.

The manager-record sequence has additional mutation boundaries. `95A620` calls `95BC40` after its `959750` message-0Dh dispatch and before returning at `95A678..95A685`. In the caller, the word copied from Window +1E8 to prepared record +14 is tested; when nonzero, `95B55A..95B56C` calls the object's virtual +00, **reloads** the pointer from record +14, then invokes that reloaded object's virtual +10 with Window interface +4. Only after these calls does `95B57E..95B58C` copy Window +14C to the record. The callback can replace the record pointer or mutate the Window and matrix, and a zero/invalid replacement is not safely modeled here. Caller-admitted pointer validity, callback effects and post-call state are required before reproducing or interpreting the copied matrix.

## Authored parent size admission

The controlled local fixture can opt into deriving the parent 966 rectangle from the pinned SPUI payload rather than supplying its dimensions. Replace `parent_966` in the local example with `"admit_authored_966":true`; retain `screen_origin_966` and `admit_identity_translation:true`. The loader validates the 969 -> 968 -> 966 -> 963 links, requires the expected authored 966 rectangle `[-7,-242,315,-55]` and absence of its serialized procedure property, and uses its 322 by 187 span in the existing 963 SimpleLayout calculation. With the same hypothetical origin `[100,200]`, this gives `[98,213,340,363]`, exactly matching the explicit-parent fixture.

This admission asserts that 966's authored span survives the live loading, event and layout paths described above. The serialized procedure omission does not prove this assertion. The origin and identity translation remain caller inputs, and the source selection, effect state, native draw, compositing and placement remain unverified. This option does not enable an automatic or onscreen HUD and is not evidence of a retail position.
