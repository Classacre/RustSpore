# Cell modified-input pick: bounded static branch

The installed `D:/Games/SPORE Collection/SporeBin/SporeApp.exe` SHA-256 was checked in this pass as `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. The following x86 instruction windows were decoded directly from PE-mapped executable bytes with Capstone; no original instructions or game ran. The REA session reported its Ghidra provider unavailable because `GHIDRA_INSTALL_DIR` is not configured, so this is **not** a new Ghidra analysis. It extends the conditional callback path and earlier retained Ghidra/static evidence in [the player-input trace](cell-player-target-input-static-v1.md) and [pick-tree trace](cell-mouse-pick-tree-static-v1.md).

`E6C8C0` forwards its four received words to `697540` before testing the low two bits of the fourth word at `E6C8F8`. When either bit is set, the branch at `E6C9C2` differs materially from the clear-bit `E6C7E0` path:

1. It calls `67D830`, obtains the manager's virtual `+58` result and calls `7C40D0` using the handler's second and third stack arguments as float words (`E6C9C7..E6C9F4`). This branch does **not** call `7C42A0`, the helper that reads the separately sampled cursor provider. The source context that produces the two event-coordinate floats, the actual camera object, float environment and pointer lifetime remain conditional.
2. It passes the two resulting ray buffers to `E87270`, together with global root `+40FC`, capacity `0x200` and binary32 maximum finite `7F7FFFFF` read at `01485C98` (`E6C9F9..E6CA29`). The prior tree trace describes conditional pending-entry flush and traversal-order output; the query is not a nearest-hit sort.
3. If the returned EAX word is nonzero, the caller copies the first returned buffer word at local `+24` to global state `+C0` (`E6CA2C..E6CA3A`). If EAX is zero, it makes no `+C0` write in this local branch. In both cases it returns low-byte 1 (`E6CA40..E6CA4A`). The nearby code does not resolve that word through the actor pool or apply the `E620D0` / `E6B560` filters used by `E6C7E0`; this is not proof that it is a valid actor, current player, or a gameplay selection. EAX is used as nonzero here; a negative or corrupt return is not separately rejected by these instructions.

The direct store is to `+C0`, not the `+C4` word consumed by `E6F620`. The clear-bit branch calls `E6C7E0`, resolves and filters actors, and conditionally stores or clears `+C4`. No local `+C4` write is decoded on the modified-bit branch after its dispatch, but the earlier `697540` call and other invoked code have not been proven free of aliases or indirect mutations; no global no-write claim follows. The meaning and consumer of state `+C0`, the modifier bits' upstream source, and ordering relative to the player controller remain open. Initializer window `E54301..E54315` stores the same EBX value to `+C0` and `+C4`; this alone does not establish EBX's value or lifecycle without the enclosing function's full trace.

For actual application integration the next precise trace is the read/consumer and lifecycle of this `+C0` state, alongside the unresolved active manager `+58` camera setter and event dispatch described in [the camera-manager search](cell-camera-manager-scan-v1.md). A bounded source model could accept explicit event coordinates, camera state, query result and source float policy to represent the conditional store, but it must not equate `+C0` with `+C4`, invent actor filtering, or attach it to the prototype's keyboard axes. No application code was changed by this trace.

## Follow-up: call boundaries and bounded consumer search

`E6C8D1` loads the fourth incoming word into EBX before `697540`, and `E6C8F8` tests its saved low byte after that call. This relies on the x86 callee preserving EBX; it is not a fresh read of the original argument after the callback. On a nonzero query result, `E6CA30` reads the first result word and `E6CA34` **reloads** the state owner from `016B4BEC` before the `+C0` store. The destination is therefore the post-query owner, not necessarily the owner supplied to `697540` at entry.

The native branch tests only nonzero EAX, so a negative return also enters the load and store. A safe controlled fixture must independently admit a count of at least one and an initialized first output word; that fixture precondition is stronger than the source branch and is not a claim about the query's guarantees.

A limited byte-signature search of `.text` for immediate address `016B4BEC`, followed by Capstone decoding up to 400 bytes after each candidate `mov` and looking for the same destination register used with displacement `+C0`, found the initialization store `E5430A` and modified-branch store `E6CA3A`; it did not establish a direct consumer. This is a heuristic, not complete dataflow: register copies, saved aliases, intervening register writes, indirect calls, different encodings, and control flow are not resolved. No conclusion that no consumer exists is warranted.

The same inspection identifies additional conditional `+C4` writes at `E5B224`, `E5B29F`, `E5B330`, and `E5B3A2`, in blocks testing state bitfields and updating vector-like values. These stores use EBP; its value, enclosing control flow and any connection to `+C0` remain to be traced before attaching semantics. The shared initializer writes do not by themselves bridge `+C0` to `+C4`. Next useful work is function-bounded dataflow of the state pointer and these stores, including aliases and callback effects, using an available Ghidra project or equivalent complete control-flow analysis.

## Headless Ghidra follow-up: E5B160 target clearing

A fresh Ghidra 12.1.4 project at `target/ghidra-input-c0-v1` imported the same SHA-256-pinned PE with `-noanalysis`; selective disassembly/decompilation seeded `E5B160` and `E6C8C0`, completed successfully and reported bodies `E5B160..E5B521` and `E6C8C0..E6CA4C`. Script and logs are retained there. Loader warnings and unresolved library links apply. Manually seeded, unanalyzed decompiler output is corroboration rather than authoritative signatures or dataflow; notably its `E6C8C0` first-result expression is incorrect relative to the actual stack load at `E6CA30`.

Instruction decoding shows `E5B16E` saves EBP, `E5B17B` zeroes EBP, and the four stores at `E5B224`, `E5B29F`, `E5B330`, and `E5B3A2` write that zero to state `+C4`. Within the decoded function body no instruction writes EBP between the zero and those stores; this conclusion assumes normal x86 callee-save behavior across calls. Entry first resolves the handle at `[[016B4BE4]+411C]` with `B71CC0` and takes the exit branch at `E5B17F` when the returned pointer is zero. The stores occur only in their respective nonzero bit-test branches; the blocks also adjust three float words using globals and write byte 1 to `[[016B4BE4]+5190]+E0`. They are target-clearing paths, not evidence that `+C0` supplies a target. Exact input bit meanings, caller scheduling, pointer validity and callee side effects remain open.

Neither the selective `E5B160` decompilation nor decoded body identifies a direct `+C0` read. This does not rule out an indirect read or mutation in a callee, aliased state, or a separate consumer. There is therefore still no established `+C0`-to-`+C4` bridge; further analysis must follow consumers and indirect calls rather than assign semantic equivalence.
