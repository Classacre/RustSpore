# Cell UI progress control value route v1

Static observation of installed base `SporeBin/SporeApp.exe`, SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. Addresses are virtual addresses. The observations below were decoded read-only with Capstone from PE section bytes using the digest-checking `tools/cell_schema_probe.py` SourceImage. They do not establish runtime execution, active layout/package, on-screen appearance, or gameplay names for the fields.

## Objects and setup

* `E00B60..E00BC7` writes object vtable `147FC3C`, and secondary interface vtable `147FC2C` at +4. `E020B0..E021F1` allocates a UI object (allocation label `UI/cSPUIGlobalOptions`), calls `811E30` on it with key at `15A586C`, and registers callback `E01940` through `80FDA0`. That callback branches to `E01610` or `E00C80` according to its byte argument. `E01610` looks up root `FFFFFFFF`, `0615B50D`, `064C23F8` and other conditional controls. This route is separate from the Cell layout at +90; its key is not `GlobalUICell-3`'s previously audited key.
* `E28480..E284E1` sets vtable `1481CB8`, retains its first pointer argument at +8, and copies five words from the second argument to +14..+24. The Cell initializer passes layout +90 and `1485ED0`, whose five static words are all 2, and retains the constructed object at Cell global +94. `E296F0..E2980B` looks up `051B54C0`, `051B5168`, and `051B7E48`, reads virtual +38 rectangles, and calls `E289B0` with values derived from those rectangles. The allocation label at `1481CC4` reads `UI/cUINewProgressBar/ProgressCursorAnimator`. This label supports a progress-control interpretation, not a particular gameplay meaning.

## Cell update and values

At `E6CAB6..E6CAF4`, the exact data path is:

1. Load `P = *( *(0x16B4BE4) + 0x5190 )`; load `P+1C` into ECX; call `E51290`; preserve EAX in ESI.
2. Call `E5BE20`, which independently reads `P+1C` and returns an x87 value.
3. Reload P, subtract the integer at `P+2C` from ESI, push that integer, store/pop the x87 result to the other argument slot, then call `E29810` with ECX = `*( *(0x16B4BEC) + 0x94 )`. Thus the first stack argument is the float and the second is `E51290(P+1C) - P+2C`. This is a static callsite, not a captured tick.

`E5BE20..E5BF67` maps signed `P+1C` to a piecewise x87 value with thresholds 200, 400, 600, 800 and 1000; at 1000 or greater it returns 1. For each lower interval it calls `1041E40(low, high, float(input))`, using interval bounds 0/200, 200/400, 400/600, 600/800 or 800/1000. `1041E40..1041E56` computes `(input-low)/(high-low+epsilon)` where the stored binary32 epsilon is `1.52587890625e-05`. The first interval multiplies by the stored binary32 0.2; the second adds 1 before multiplying by 0.2; remaining intervals multiply by 0.2 then add stored binary32 0.4, 0.6 or 0.8. Preserve these operation orders and float conversions for exact replication; negative inputs are not explicitly clamped by this function.

`E51290..E5131D` selects rows at `14846C4 + 0x1C*i` by scanning signed threshold at row +4. Input 1000 selects `1484910` directly. At an exact threshold it returns integer row +8; otherwise it calls `E51230` to interpolate row +8 against the next row's +8, using row +4 and next row +4 as endpoints, stores the x87 result to binary32 and converts it to integer by `CVTSS2SI` (MXCSR-dependent rounding). The static threshold/output pairs for supported 0..1000 start `(0,0), (50,5), (100,10), (150,13), (200,16)` and end `(900,58), (950,61), (1000,65)`; values must be read from the authenticated source for a complete table. The scan has no demonstrated upper bound outside this domain and negative input has different row behavior. This proves a table-derived integer, not what the integer represents.

At `E2982D..E29949`, when the integer argument differs from object +34, the routine looks up `ABCD1001`, formats that argument through `8824C0`, and calls the control's virtual +80 with the resulting string. The formatting and virtual implementation are not fully resolved. At `E29BD3..E29C20`, when the float argument changes relative to object +28, `E283A0` uses the five copied words to calculate a segment/index and local fraction; it looks up control `051B54C0 + index`. At `E29C38..E29C8B`, it also looks up `051B5168` and computes a horizontal coordinate from the chosen control's +38 rectangle and the local fraction, followed by animation calls. The update subsequently calls `E289B0` at `E29F15`. These are conditional static paths; no semantic equivalence with prior IDs `05AF4AF0..2` / `05AF4BF0..2` is established.

## Remaining evidence needed

Trace writes and lifecycle of `P+1C` and `P+2C` to named gameplay operations, including how the stored value changes during controlled Cell actions. Resolve the actual control implementations, `ABCD1001` formatting/localization, and screen-specific SPUI bindings; authenticate the selected provider/package and observe a live update before asserting an original HUD mapping. A source label alone cannot name the producer or prove visibility. The REA MCP server returned `provider_unavailable` because its process lacked `GHIDRA_INSTALL_DIR`; these findings use verified executable bytes, not fresh decompiler results. Existing conditional sizing and source-candidate limitations remain in `cell-ui-parent-sizing-audit-v1.md` and `cell-ui-candidate-audit-v1.md`.

## Feeding producer and dispatched-value follow-up

`E7D0A0` provides a source-backed feeding route into `P+1C`: a present resolved definition supplies its integer `+30C`, while an absent/special definition uses 10; a present zero exits before this accounting. The source schema audit identifies that `cEatData` member as `foodValue` (see `cell-behavior.md`, its `cEatData` schema and eating sections, and `cell-source-health-integration-proposal-v1.md`). At `E7D2AB..E7D2B5` the value is passed as the first integer argument to `E7CE40`, whose `E7CE91..E7CECB` adds it to `P+1C` and caps the signed result at 1000. The flag and earlier conditional call matter; the bounded accounting model and its 1,504-case comparison do not validate the complete runtime feeding path. Other P+1C writers and the relationship to a prototype food event remain unresolved. This establishes a food-value-to-progress-bar path under the stated branch, not a license to map prototype mass to original foodValue.

One observed writer of `P+2C` is `E809D0`. At `E809D5..E80A01` it passes an incoming object to `E82CB0`, which copies object +0C, byte +44, integer +34, and three words +18..+20 to caller locals. At `E80A04..E80A40`, only when object +0C equals `01100000` and byte +44 equals zero, it sets `P+2C = E51290(P+1C) - incoming_object+34`. Consequently, immediately after that write, and only if neither input changes before consumption, the integer passed to `E29810` equals the object +34 word modulo 32-bit arithmetic. `E80B53..E80B6D` additionally writes `E51290(P+1C)` to P+30; it does not identify the object's value. This is one writer and does not establish initialization, persistence, or all updates of P+2C.

Cell initialization registers callback `E809D0` for message ID `030C11C7` through the manager returned by `67D7E0` (instructions `E81B83..E81B9F`); teardown removes the registration at `E81BEE..E81C09`. The manager's virtual dispatch implementation and actual delivery are not established. A candidate send path is `57BD30..57BE1B`: under its state and pointer guards it passes its retained +4BC object to `57A360`, which calls that manager's virtual +18 with message ID `030C11C7` and the object (`57A373..57A387`). A related object population path `57E60A..57E61F` loads the provider at owner +434, calls its virtual +4 with argument zero, and stores the return at the retained +4BC object's +34. `57E5CA..57E5D0` clears that object's +44 on that path. The connection is conditional on object identity, no intervening replacement or mutation, and successful message dispatch; static proximity alone does not prove this precise population and callback occur in one execution. Other senders and object construction/initialization routes may exist.

The provider's concrete identity, virtual +4 implementation and semantics, and the object's +0C value at dispatch still need source or runtime evidence. Trace owner +434 construction and vtable, its channel-zero mutations and the bounded sender-to-callback lifecycle before interpreting the integer as a particular currency. These raw address observations were independently decoded from the same SHA-256-pinned executable; no game execution or UI integration was performed.

## Candidate channel-zero provider

A static constructor path at `584308..584376` allocates 0x30 bytes, initializes vtable `13F5680`, installs that pointer at receiver +434, and calls `59EB60` with six. This matches the owner-relative offset used at `57E60A`, but receiver identity and runtime path must still be proven before equating them. The vtable's +4 slot is `59E340`: it loads the array pointer at receiver +8 and returns its 32-bit element at the supplied index; with argument zero the observed expression is `*( *(provider+8) + 0 )`. The +24 slot is `59E310`, which writes a supplied indexed value when different, calls virtual +1C, and calls `5A7850`. The +20 slot `59E2E0` adds a supplied delta to an indexed element and makes those same calls when the delta is nonzero. `59EB60` requests six elements each for arrays at +8 and +1C; the initial fill and allocator behavior need separate verification.

At `57BF40..57BF69`, an owner-relative +434 provider's virtual +24 is called with index zero and the incoming argument object's +8 word. At `57BCBE..57BCE2`, a separate path reads index zero through virtual +4 and, if below a local value, sets index zero to that value through +24. With vtable `13F5680` admitted, those are concrete channel-zero read and set operations. In addition, virtual slots +2C and +30 point to `59E260` and `59E280`: those routines obtain an argument object's +5E4 word and pass respectively that word or its negation as a channel-zero delta through virtual +20. The argument object's type and +5E4 semantics remain unresolved; a separate +30 virtual call on a channel provider is visible at `57BC9C..57BCA8`. These bytes support an indexed integer ledger with both positive and negative changes; they do not by themselves identify it as DNA or prove the complete editor-to-Cell round trip.

`57BE40..57BE82` allocates and installs the retained +4BC object via constructor `5798B0`; that constructor sets primary vtable `13F5674`, secondary vtable `13F5670`, and zeroes +34 and +44. `57BE95..57BEA7` copies the object at owner +1CC's +90 word to the retained object's +0C. A later same-owner path populates +34 and dispatches it as described above, but the provenance and runtime value of owner +1CC's +90 are not established. Therefore even the necessary `01100000` callback guard remains conditional.
