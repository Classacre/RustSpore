## Canonical index correction and both variants

The follow-up above used obsolete shape labels. `re/archive-index-native.md` records the installed executable's `8DAFE0` reader and the independently checked canonical flag interpretation. For Audio1, flags `6` mean common scope `021407EE` and common instance-high zero; each record supplies type, instance-low, offset, sizes, and optional metadata. The former `index_record_slot` values `00010000` are metadata words, not scopes. Likewise the `0001FFFF` previously called the event group is metadata: both event keys are `(instance 34C2FF0B, type 02B9F662, scope 021407EE)`. The canonical `NativePackageIndex` already supports this layout; it was not necessary to add a second reader.

A fresh independent Python canonical-index pass (`target/collision-audio-independent-v1.txt`) finds 17,651 Audio1 records and 17,651 unique full native keys. Type counts are `01A527DB` 17,538; `0497925E` 43; `02C9EFF2` 18; `03055F61` 15; `617715D9` 11; `029E333B` 7; `01EEF63A` 6; `022D2C83` 4; `2B7DF427` 3; `00B1B104` 3; `03F51892` 2; `2081B4F5` 1. For each of the 20 raw entries in each event variant, the little-endian first-word hypothesis yields exactly one instance match across *all* Audio1 records, not merely one matching type. All 20 are distinct and each has type `01A527DB`, scope `021407EE`; the independently decoded lengths and hashes for both variants are retained in that report. Both sample arrays are byte-identical (type `0020`, flags `009C`, count 20, stride 12), although the full event payload hashes differ as stated above.

`crates/spore-bevy/examples/collision_audio_candidates_v1.rs` provides a reproducible canonical Rust inspection of both named providers and all matching Audio1 records. It emits raw entries, all instance matches, full keys, payload lengths/hashes, type census and before/after package hashes. This is a conditional candidate join: the event consumer, field endianness, native reference decoding, mounted priority, contact conditions and selected sample are still unproved. Matching package hashes at the ends of the run do not establish that a file was held stable between reads. No playback or gameplay mapping is asserted.

The Rust example was built and run with `tools\build.bat run -p spore-bevy --example collision_audio_candidates_v1 -- <Audio1> <PatchData> <Audio2>`. Its retained JSON is `target/collision-audio-candidates-v1.json`. A separate Python comparison checked both variants and all 40 rows for identical raw records, all-instance match counts, native key type/scope, decoded lengths, and SHA-256; all agreed. Input package hashes before and after this inspection respectively were Audio1 `54a46c03e921c2d8b5cf0d3998935f665fa53d1267d257dc85e8b90d94cee572`, PatchData `cadbff237076b441e6981503f80538705aefa5863bb4c8d1b869f9db98d1adff`, Audio2 `bc17f2f6c18ad4277bb9c605a8359c9be14300abf3e626077bb21ec6b5c13dfb`. ### Reproducible comparison follow-up

The prior independent Python comparison was initially run as an ephemeral command. Its reproducible successor is `tools/collision_audio_compare_v1.py`, using the separate Python canonical index decoder and event walker. Run it on `target/collision-audio-candidates-v2.json` with a new output path; the retained successful receipt is `target/collision-audio-comparison-v3.json`. It verifies both event payload hashes, both 20-row arrays, each candidate's full key, metadata, decoded length and payload hash, and the Audio1 record/type/unique-key census. It also hashes each named package before and after its own reads and checks those hashes against the Rust report. The earlier v2 comparison receipt uses the overly broad field name `audio1_records_compared`; v3 corrects this to `audio1_records_censused` because individual non-candidate rows are not compared. All three identities and both endpoint hashes are labeled in the Rust v2 report. This check verifies agreement of implementations and observed bytes, not continuous stable-file admission, event-reference semantics, or gameplay. The Rust report is exploratory: it displays match counts, candidate types and total count without treating any particular count, uniqueness or type as an acceptance gate.

The successor receipt `target/collision-audio-comparison-v4.json` binds the comparison script and its four local direct/transitive imported modules by path and before/after SHA-256, in addition to the Rust report and input packages. It records the observed count distributions explicitly: 17,651 Audio1 records and 17,651 unique full keys; each variant has 20 distinct candidate instances, each with one Audio1 match, all of type `01A527DB`. Imports occur before the first implementation hash, and matching endpoint hashes do not prove continuous file stability. The receipt is evidence of this exploratory comparison, not native reference resolution or an acceptance gate on those observed counts.

After correcting numeric scalar endianness, the sample-array path was rerun with Rust report `target/collision-audio-candidates-v3.json` and independent receipt `target/collision-audio-comparison-v5.json`. Both 20-row arrays and their candidate keys, sizes and payload hashes still agree. This does not resolve runtime provider, sample selection or playback; the same source-path and implementation-hash limits apply.
