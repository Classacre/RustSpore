# Civilization candidate factory dispatch boundary

Static source evidence only, SporeApp.exe SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. Independent Ghidra 12.1.4 `-noanalysis` projects, scripts and logs are in `target/ghidra-civ-factory-init-v1/` and `target/ghidra-civ-factory-dispatch-v1/`; the latter includes PE-mapped instruction bytes and image table values. Loader warnings and manual function boundaries apply. No runtime observation is claimed.

A static initialization path at `F47E2A..F47E50` requests `148h` bytes, calls `920220` only for a nonzero allocation, stores the result at owner +24, and passes it to setter `91FB70`, which writes global `01668B64`. `920220` installs table `0143E47C` at object +0; the image table +20 is `91FBE0`, +24 is `91FBA0`, and +14 is `920510`. A separate teardown path initializes EBX to zero at `F475F7`, then at `F477DD..F47805` conditionally calls the setter with EBX; this is zero assuming intervening calls preserve EBX according to the calling convention and then may invoke an owner +24 virtual destructor. These paths do not prove which object or table is present at the later call, nor preclude replacement or callbacks. Construction, allocation, owner lifetime, table state and ordering remain admissions.

For admitted `0143E47C` dispatch, `91FBE0` invokes receiver virtual +24 with three supplied values. If the result is nonzero it calls the returned object's virtual +0C with another supplied value; nonzero result returns directly, otherwise virtual +0 and +4 execute before zero returns. Reloads and callbacks can alter tables, state and lifetimes. If the receiver's +24 slot is still `91FBA0`, then a zero third supplied argument causes a virtual +14 lookup using the first supplied argument; a nonzero third argument is used directly. A nonzero object then receives virtual +8 with the first and second supplied values. Failure returns zero. Although the image +14 slot is `920510`, lookup contents, object callback target, requested record, and concrete returned class are not established. No constructor or cVehicle identity follows merely from these slots.

The preceding `FF0FB0` path selects a triple from a distinct caller-supplied array base. Its producer and selected values remain unresolved; the static selector indices in `civilization-vehicle-receiver-selection-v1.md` are not actual asset keys. Next trace admitted `920510` registry population and selected factory +8 object against the record value, and separately identify the caller-supplied array producer. No vehicle art or renderer change is justified by this evidence alone.


The image +14 target `920510` acquires a helper on receiver +8, calls `A68330` on receiver +108 with the incoming key, and traverses the resulting bucket/range. It examines a contiguous run of matching node keys and stops at the first nonmatching node; within that run it retains the first candidate or replaces it when a later node's +8 is greater under signed comparison, returning that candidate's +4 pointer after releasing the helper; if none is found it returns zero. The helper must supply an appropriate start and range for any broader lookup interpretation. This observation requires valid helper behavior, bucket and node structures, traversal termination, lifetimes and callback effects; insertion order, registry population, class identity and actual lookup result remain unresolved. Exact bytes are retained in `teardown-and-lookup.txt` alongside the wider teardown range showing the EBX initialization.


The standard table +4 entry `920680` is a candidate population boundary. It calls the supplied object's virtual +4 with a buffer and `80h` capacity, then for each reported entry supplies its word, the same object pointer and caller-provided priority to `91FFE0` on receiver +108. After `91FFE0`, it reloads the buffer word and calls that object's virtual +0C with the reloaded value; the earlier call can alter the buffer. When +0C returns nonzero, it passes further data to `920130` on receiver +128. The count returned by +4 is trusted and is not locally capped to the supplied `80h` capacity. The +108 location is the lookup structure used by `920510`, but helper insertion semantics, capacity/returned count, object behavior, mutation and lifetime must be admitted. This is not proof of any concrete registration or live registry contents. Exact bytes appear in `target/ghidra-civ-registry-insert-v1/instructions.txt`.

A separate static code fragment at `B24DEA` writes function pointer `B1EAF0` (the earlier cVehicle allocation/constructor path) through an EAX returned by `ECC210`; a nearby `B23CF0` call has constants `02E98AB7`, `02E98AB4`, and a pointer. Instruction alignment of this fragment was manually selected, and the enclosing routine, helper semantics, association with `920680`, runtime provider, and actual FF record key are not yet established. Those constants must not be identified as the selected vehicle asset or as a proven factory mapping. Further work should establish the enclosing routine and data-flow to the object supplied to `920680` before joining this candidate to the lookup.
