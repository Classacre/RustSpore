## Input messages and records

`8493C0` has four stack arguments and ends `RET 10h`. It uses the first with `USER32!GetWindowLongA(-21)` at `8493C9..D2`; if no associated receiver exists it calls `DefWindowProcW` with the four original arguments. With an associated receiver it can first offer an envelope to a receiver callback (`849405..464`); a consumed result skips the switch. On the remaining path, the message argument at `849468` compares with `100h`. Message `100h` calls `8486D0` at `84962D..641`. The five-entry table at `849A84` maps `101h` to `849696` (calls `8487B0`), `102h` to `8496D8` (calls `848880`), `103h` to default, `104h` to `849675` (calls `8486D0`) and `105h` to `8496B7` (calls `8487B0`). The Windows message-number interpretation is respectively key-down, key-up, character, system key-down and system key-up. These are distinct paths; `102h` is not the indexed key-down path.

The first stack value passed after the window handle to the key helpers is the original message `wParam`, held in EBX (`8493FB..405`, `849639`, `8496A2`, `849681`, `8496C3`). `8486D0` and `8487B0` copy that word unchanged to event-record `+0C`, set record `+08 = 1` and byte `+11` to 1 or 0 respectively, then call `847FE0` with envelope `01EE1001`. They sample Shift, Control, Alt and Windows virtual-key states through `USER32!GetKeyState` into a modifier byte; the down path also forms a repeat-related count from a bit of the supplied high lParam half (`848759..786`). This is an event producer under the switch and receiver conditions, not evidence that any event reached a running Cell stage.

`847FE0` first sends this envelope's record to nonzero receiver `+60` virtual `+30`; otherwise it takes the `+5C` or `+64` paths. Separately, the registered `814C80` listener forwards records through `812BC0` when its `+4C` receiver exists. Image jump table `812D64` maps incoming record `+08 = 1` to `812BDD`: byte `+11 != 0` becomes translated type 1, zero becomes type 2, source `+0C` is copied unchanged to translated `+10`, and modifiers are translated into `+14`. Repeats can set flag `40h`. As described in the earlier event-chain note, only if this listener receives the envelope, its receiver queues it, and the targeted root/listener gates pass can that translated record reach `950AA0`.

`950D18` maps translated type 1 to `950AF0` and type 2 to `950B0A`: these invoke the root's virtual `+30` and `+34`, respectively, carrying event `+0C`, `+10`, `+14`. The candidate root table `1419488` selects `814B90` and `813180`. Both have a `+28D` early gate; the key-down route additionally requires byte `+220` nonzero to call manager `+268` virtual `+2C` and then selected object's `+24`. The release path calls the same manager selection and selected object's `+28` when its earlier gates permit. The manager path and `Game_Cell` registration are conditional as in the previous note. If the selected object is the `Game_Cell` table `1486008`, those slots are `E81920` and `E50E70`; the former invokes `E82930` first and sets the bit only if its AL is zero, while the latter clears the bit through `697510`. Both bounded setters invoke `697450` after the store (`697505` and `697537`), including repeated set/clear operations. Under the normal nonaliasing object layout, `697450..697499` reads indexed bits `10h`, `11h`, `12h`, `E1h` and `5Bh` and recomputes the separate word at `+20` with masks 1, 2, 4, 8 and 10h respectively; it has no calls and does not write the eight indexed words at `+00..+1C`. The bounded snapshot model recomputes that word after admitted stores and retains the caller-supplied initial value on consumed events; it does not execute the original helper. The down callback also has a separate conditional toggle: when `E82930` returns zero, incoming second word equals 2 and code is `48h`, `E81938..E81951` toggles byte `+937` before the setter. Root fallbacks, listener consumption, callback mutation, key repeat, focus loss and pairing of actual down/up events remain outside this join.

## Names, layout and bounded next step

The image name/value table at `154CD10`, `154CEA8`, `154D098`, `154D0E0` identifies `28h` down, `25h` left, `27h` right and `26h` up. At `154CEF0`, `154CF00`, `154CF10`, `154CF20`, it identifies `62h` numpad2, `64h` numpad4, `66h` numpad6 and `68h` numpad8. These values also correspond to Windows virtual-key codes. The original image's numerical `57h/53h/41h/44h/5Ah/51h` match Windows W/S/A/D/Z/Q virtual-key values, respectively; this describes the logical virtual-key values forwarded by the admitted event route, not physical scan-code placement, text input, or a particular installed keyboard layout.

`E844A0` is separately called four times by the vector assembler. Under the specifically traced candidate provider/vtable, AL indicates equality of that provider's UTF-16 locale span to `fr-fr`; AL zero chooses `57h` and `41h`, nonzero chooses `5Ah` and `51h`. The provider's actual runtime value and even its active implementation remain unproved. This test is not the same as the OS keyboard-layout query: `GetKeyboardLayout` also occurs elsewhere at `849CB8` and `84A537`, but no join from those queries to the `E844A0` result was established.

The bounded opt-in key-event adapter accepts an already admitted Windows virtual-key word and press/release, then feeds a frozen bit snapshot and caller-supplied `E844A0` results to the indexed-vector model. It applies the `6974E0`/`697510` lifecycle under explicit root, selected Game_Cell receiver, down-gate, stable-state and nonaliasing admissions. It models `+20` recomputation on admitted set or clear, while the separate H/modifier toggle remains excluded. Tests cover opposing keys, repeats, key-up, unsupported codes, caller-selected focus handling and differing callback results. This does not prove live queue routing or justify connecting prototype thrust/turn to native target movement.
