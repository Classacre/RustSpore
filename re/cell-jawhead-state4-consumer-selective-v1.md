This is a static, conditional consumer trace, not a rendered Jawhead frame or native execution. SporeApp.exe SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a` was verified in this pass. ## Direct-draw payload and conditional consumer

The conditional fresh-object source mesh/descriptor order established in `cell-gmdl-palette-render-state-v1.md` associates Jawhead mesh 0 with `(0,64)` and mesh 1 with `(64,19)` on that path only. Direct instruction decoding independently confirms `73EEFB..73EF10` multiplies the indexed descriptor's first word by `48`, adds it to the selected matrix base, writes the result to `0162F880`, and writes the second word to `0162F874`; `73EF21..73EF2A` passes pointer `0162F870`, index 4 and flag 1 to `777990`. At `777990..7779ED`, the setter stores that pointer at `016F75A8 + 4 * index` and marks a dirty bit. Thus, absent intervening mutation, state slot 4 at `016F75B8` points to the `0162F870` payload.

`777B60` reads slot `016F75B8` and returns if null. When the payload's +8 word is zero, `777B6F..777BA3` uses payload start at +0, count at +4 and pointer at +10. It calls the object at global `016F99D0` via vtable +178 with, in push order, `3*count`, `pointer + 48*start`, and caller-supplied base plus `3*start` (then the receiver). The independent no-analysis `11FA120` path reads the same slot and uses the same arithmetic on its +8=0 branch, but does not have the first function's null check. These are conditional static consumers; the paths' runtime dispatch and the receiver's vtable identity are not established here. The function names and signatures from the selective decompilation are not evidence of either.

Combining only those admitted facts: on the direct draw and +8=0 path, the pointer argument is the selected matrix base plus `48 * (descriptor_first + payload_start)`, and the count argument is `3 * descriptor_second`. This is an arithmetic inference across the two bounded routines, not evidence that the actual call happened. The value at payload +0, the +8 mode, receiver identity and caller register base are not established by the direct-draw store itself. In particular one must not silently treat +0 as zero or assume the count is already a vector-row count.

## Nonzero +8 branch and validation boundary

For +8 nonzero, `777BC0..777BFC` and `11FA170..11FA1AD` read three unsigned bytes per iteration from payload +0C, in order: a multiplier for count, an offset for the caller base, and an offset for the source pointer. Each is multiplied by three, and the source offset additionally by 16. A signed-negative +8 causes no calls; a positive value enters a loop advancing by three, and a positive non-multiple of three can read a final full triplet beyond the nominal +8 byte extent. It invokes the same receiver vtable offset on each iteration. These operations are directly decoded, but the meaning and validity of those bytes, the full byte-array extent, the caller base, and the active branch are unresolved; malformed length/lifetime safety is not inferred.
