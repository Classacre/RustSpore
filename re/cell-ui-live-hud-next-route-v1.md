# Cell HUD provider, placement and state: next source route

This is a static, read-only analysis of base `SporeApp.exe` SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. It identifies the next boundaries needed for the actual HUD; it does not identify an active provider, frame, control state or screen position.

## Provider and root

Cell initializer `E54150` requests `GlobalUICell-3`, type `0510A95B`, and external parent `2EDD95CA`. Under the guarded registration path, resource manager `8E1440` registers the loader whose slot `10` (`80FC60`) associates that requested type with ordered alternatives including `250FE9A2`. The loader/provider and database paths, and the two differing installed SPUI and atlas candidates, are documented in [the registry audit](cell-ui-registry-audit-v1.md) and [candidate audit](cell-ui-candidate-audit-v1.md). The database list is traversed in descending signed priority with first-success behavior, but the registered product databases, equal-priority insertion order, alternate-type outcome and successful provider remain unobserved. The next provider slice is to follow the actual manifest/product registration and per-database open/query success for the exact layout and atlas keys, including aliases and resource-type fallback. A hash-checked explicit package read is a test fixture; it cannot select the native winner.

For placement, the conditional chain is Graphics descriptor -> queued Window manager resize -> root Window -> `UIWorld_GlobalUI` -> loaded layout root -> local procedures, as detailed in [parent sizing](cell-ui-parent-sizing-audit-v1.md) and [descriptor trace](cell-ui-graphics-descriptor-source-trace-v1.md). The external dimensions, callback/queue ordering, root matrix and later mutations are runtime inputs. A useful next bounded fixture should feed the actual manager-root width/height and parent transform at the resize boundary, apply the observed root attachment and layout propagation to the candidate graph, and compare resulting control rectangles against independently captured or isolated source `+38` reads. The dimension source and actual initialized runtime values still need provenance; a supplied width is not a capture.

## State and visibility inputs

Bounded PE instruction decoding adds a concrete handoff to [the StdDrawable trace](cell-ui-std-drawable-dispatch-v1.md). In `960430`, if receiver +1E0 is nonzero, `9604AF..960520` copies the raw word at receiver +AC into the first word of a local record, forms `[0,0,receiver+90 - receiver+88,receiver+94 - receiver+8C]`, and calls the drawable's virtual +10 with the graphics receiver, that rectangle and a pointer to the record. Under the separately established StdDrawable vtable association, `987D75..987D7D` reads the record's first word and supplies it to `987A00`. That selector uses low state bits and the eight resolved pointer slots. This is a conditional dataflow from the window's +AC word to source image selection; +AC's meaning, initialization, actual value, mutation, and object identity are not established. Do not equate the word with a particular named state or assume serialized null sentinels were resolved.

At `96043B`, the high byte of receiver +1DC controls an earlier background-color draw branch; it does not by itself gate the separate +1E0 drawable call. At `95A6A2..95A6D4`, the inspected tree-builder branch requires byte +30 bit 2 clear and either bit 0 of that byte or bit 0 of byte +2C set before its admitted route. These are raw tests on the supplied object, not a proved semantic visibility label or proof a particular candidate segment is visited. Later code, parent eligibility, clipping, effect animation, child attachment and mutation still matter. The exact bounded instruction records are `target/source-ui/cell-ui-draw-input-trace-v1.json`, SHA-256 `cb9736f6146bedc78a7173d5437b01063ad8c57a520912d0dc929123037775e4`; the PE identity was checked before decoding. It is local ignored evidence and is not runtime execution.

The next narrow state trace is to establish the concrete Window constructor and deserializer for the candidate controls, find writes/virtual setters of the same object's +AC and +2C/+30 bytes, and follow their callers and callback ordering through `E296F0`/`E29810`. Separately verify that `EEC1B007` has resolved to the expected StdDrawable and that its slot pointers have been resolved for the selected package. A guarded model can then take an explicit post-deserialization/post-update snapshot and compute the source selection and eligibility; a live claim additionally needs same-object identity, callback/pointer lifetime, and runtime mutation evidence. Segment progress and cursor arithmetic are useful inputs to that later trace, but do not establish visibility or a full HUD.

## Base Window constructor and explicit state write

The base Window factory `956E10` calls constructor `9629F0`, whose allocation-base primary vtable is `14417BC` and whose +4 interface vtable is `1415638`; the primary slot +24 contains `960430`. On that constructor path, `962A33` stores 3 at allocation-base +2C, `962A3A` stores zero at +30, and `962AD0` stores zero at +AC. The earlier EBX-zero provenance is documented in [the Window trace](creature-source-frame-overlay-v1.md). These are initialization writes, prior to deserialization and callbacks. The generic descriptor associates serialized `EEC1B000` with allocation-base +2C; the installed payload's property and successful application must be established per object. A constructor default is not a later frame value.

The base +4 interface table's +58 slot points to `95FE90`. For that specific interface, `95FE96..95FEA4` compares and conditionally writes interface +A8, which is allocation-base +AC. If the value changes it invokes interface +114 with a local event record containing type `13`, then, if interface +1DC is nonzero, invokes interface +90; `95FEC1..95FEDE`. Both are indirect and may have side effects, including mutation, so the value passed to the setter is not proof of the state subsequently read by the drawable. Distinguish the interface-relative offsets from the allocation-base offsets; another vtable or object cannot be assumed to use this mapping. The Cell progress-control calls have not yet been tied to this setter on the same allocated Window, and no conclusion about active visibility follows.

`spui_window_draw_state_v1` implements only the three constructor fields, the explicit pre-callback comparison/write boundary, the observed `95A690` tree eligibility predicate and selection through the existing explicitly resolved StdDrawable slot model. Its caller must supply any post-callback snapshot and slot occupancy; it neither executes the event nor predicts the full draw tree. It is not wired to the experimental frontend. Focused tests cover these bounded rules; they are Rust tests, not original-instruction comparison or live state evidence. The next source task is to identify the concrete progress Window instances after graph deserialization, trace calls to interface +58/+7C and listener events through update and attachment, and snapshot their later flags, state and resolved drawable identities before treating any result as an active HUD.

## Conditional proportional-listener registration

All five segment windows in both pinned layouts contain exactly one serialized `EEC1B00C` reference to a distinct `AF3DF411` ProportionalLayout. For PatchData, Window/listener index pairs are 143/134, 155/146, 166/157, 177/168 and 191/182; Spore_Graphics pairs are 144/135, 156/147, 167/158, 178/169 and 192/183. Serialized references establish neither successful object resolution nor lifetime. Each listener has the decoded four-float proportional property, already covered by [the graph audit](cell-ui-progress-graph-audit-v1.md).

The `97EB90` factory constructs a 0x20-byte ProportionalLayout with primary vtable `1444230`. Under that exact class and vtable, query `97E7F0` delegates a request for listener interface `2F009DD0` to `950D90`, which returns the allocation-base object; priority slot +10 `A6C920` returns zero and mask slot +14 `97E820` returns `108h`. Thus, conditional on the serialized `EEC1B00C` handler being invoked on the same constructed Window, successful reference/interface resolution, allocation and insertion, `961E10 -> 961FB0` registers that specific listener on that Window. The registration calls `9614F0` on the Window after linking; if the inserted `108h` mask remains present and traversal completes, its bit `100h` sets Window allocation-base byte +31 bit `02h`. That bit independently satisfies the child dispatch predicate in `960B8E` when the parent actually enters its changed-span relayout loop. Other nodes and callback effects can affect other bits or later state; a linked listener and relayout are not live observations.

The same table maps listener event dispatch +18 to `950DF0`. Direct registration event `1000h` reaches its +60 slot `DF5080` (a return-only routine), and the owner-present event `11h` maps through generic dispatch to +50 `A20700` (returns zero). For a later event `10h`, the static manager event-mask table yields `108h`, matching the listener mask; conditional traversal to this node reaches `950DF0`'s +58 and hence `97E8A0`. With the base Window interface vtable, that handler calls interface +10 `95FAE0` to obtain the linked parent via child allocation-base +38, then parent interface +38 `95FB20` to obtain parent allocation-base working rectangle +88. It invokes the proportional +0C interface callback `97EA70` with that rectangle and the supplied working rectangle and clamps inverted edges. This narrows the same-Window-to-parent arithmetic path; it requires a valid non-null parent, unchanged vtables, successful dispatch without an earlier listener stopping it, fresh working rectangles and stable references. Later floor, matrices, effects and draw ordering remain separate. Event `13h` maps to mask `10h`, which does not intersect this listener's `108h`; this alone does not exclude other listeners or the setter's other indirect callbacks from mutating state.

`spui_window_listener_flags_v1::reduce` models only the `9614F0` reduction of an explicit freshly supplied mask list and indicates a pending owner callback when its bit-zero change and gate require one. With a sole supplied mask `108h` it sets +31 bit `02h`, and the existing child-dispatch model accepts that input. `tools\build.bat test -p spore-core spui_window_listener_flags_v1` passed 2/2 synthetic tests. This is not native execution, a list implementation, listener registration or callback completion. The bounded static instruction and table record is `target/source-ui/cell-progress-listener-static-v1.json`, SHA-256 `cb4d5af2ec2eefb89849064cd712cf59ca47191efa8c12db9d25f1100f51a33e`, generated from the hash-checked PE. ## Five explicit local rectangles

`cell_ui_five_local_fixture_v1` now composes the existing source-decoded `ProportionalLayout`, clamp and floor operations for all five segments. It accepts a caller-selected pinned layout package, positive finite parent spans encoded as binary32 bits, and an explicit stable-package, one-dispatch, no-other-mutation admission; it requires each segment's unique Window and one valid referenced proportional listener.
