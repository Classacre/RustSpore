# Cell camera state and auxiliary view: static evidence

This note uses the installed SporeApp.exe SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`; all addresses are virtual addresses in that image. It does not use the editor thumbnail camera as evidence for Cell gameplay. No native executable or GPU code was run for this analysis.

Retained Ghidra dossier `target/rea/20261028-source-runtime-v6/20-analyze_function.json` describes stage setup `E5D9E0`. Raw disassembly at `E5D9E6..E5D9ED` calls `7C4770(0)` with ECX = `016B5298`. The same setup creates named Cell skybox, background and main worlds. `E54990` prepares an object containing `016B5298` and passes it through a virtual call on an object obtained from CellSkyboxEffectsWorld +161B0; `E54A60` similarly uses the background model world +161C0. This supports an auxiliary Cell camera-like object, but not its identification as the primary gameplay camera.

At `E54890..E54981`, a global state pointer at `016B4BEC` supplies three floats +48/+4C/+50, and a second vector adds +6C/+70/+74 plus a scalar times the global vector at 015A8C40..48. These vectors and a global vector at 015A8C34 are passed to `10436F0`, whose arithmetic begins by subtracting the vectors, normalizing and computing cross-product terms. The resulting 16-word matrix is passed to `7C45E0` on `016B5298`. Calls to `7C4CD0`, `7C4540`, and `7C4560` configure the same object's perspective-like and scalar state; exact final projection values and runtime conditions are not established here. `7C45E0` begins by copying all 16 input words into the camera-like object and then derives additional fields. `7C4CD0` uses tangent and stored viewport ratio to update fields of the object at +170. These are static operations, not a recovered main-camera frame.

Retained dossier 36 (`E54150`) initializes state +48/+4C/+50, +54/+58/+5C, and +60/+64/+68 from the same three globals, and initializes +6C/+70/+74 from (0,0,20). Dossier 250 (`E7D8B0`) conditionally writes the first word of its actor argument into state +E0 and copies current +48/+4C/+50 into both +54/+58/+5C and +60/+64/+68. Dossier 121 (`E79750`) also writes an actor-related word to +E0 and passes state +48 to `E5E960`. These facts establish conditional linkage between actor-related state and this camera-related state; they do not prove which actor is active, that +E0 is dereferenced as a position, a per-frame update cadence, or exact world-to-view mapping.

Stage setup calls the singleton returned by `67D830` through virtual offsets +50 and +58 (`E5DA9C` onward). Its concrete implementation, live camera resource key and class, actual main-camera attachment, and source of the per-frame anchor remain unresolved. They must be traced before treating the auxiliary matrix as the main scene view or reconstructing shader uniforms. The fitted editor thumbnail camera is a separate path.

The `67D830` singleton has a statically recoverable implementation. `7E8D82` calls `7D8AF0`; `7E8D9F` stores its returned pointer at the owner +C8, and `7E8DB2..7E8DB9` publishes it via `67DA20` to the singleton word `015FE8B0`, returned by `67D830`. `7D8AF0` installs primary vtable `014130C0`. This table's +50 slot is `7D8170`, returning object +2C; +58 is `EF4800`, returning object +30. Thus `E5DA9C..E5DABC` retrieves those two manager fields. The retained stage setup shows the first field passed to virtual +140 on the background, beach and main model worlds. This is manager-to-world attachment evidence conditional on that implementation and successful initialization, not identification of the selected camera resource, target object class or dynamic view state.

Manager initialization is distinguishable from selected camera creation: primary vtable +0C points to `7D7D80`, which on its first-initialization branch calls `7C70D0`, stores the result at manager +2C and invokes its virtual +10 with `01412FC4`. `7C70D0` allocates 0xB4 bytes and calls `7C6FB0`, which installs primary vtable `01410688`. Manager virtual +54 resolves to `7D8180`: it stores its supplied word at manager +30 then forwards that word to manager +2C object's virtual +18. Thus the +2C manager-owned object and +30 supplied value must not be conflated. This does not yet identify the +30 setter's Cell-stage caller, selected resource key or class.

The +2C object's primary vtable `01410688` gives +18 = `7C5A70`, which stores its argument at object +B0, and +1C = `7C5A80`, which returns +B0. Thus `7D8180` forwards the same supplied word into +B0 as well as storing it at manager +30. The +2C vtable's +28 slot points to `7C64F0`, the resource-enumeration routine discussed in `cell-camera.md`; this links the constructed +2C object to that routine without equating the editor preset to the active gameplay camera. A bounded direct-call scan of Cell-region references to `67D830` found uses of manager getters +50 and +58, but did not establish a +54 setter call or the provenance of the active +30 value. Indirect callers and other code remain to be traced.

The argument `01412FC4` passed by manager initialization is the image's null-terminated ASCII string `camera`. This labels the initialized +2C service; it is not a PROP key or selected camera class.
