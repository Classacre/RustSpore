# Blockdata lookup and producer linkage: static leads

Target: `D:\Games\SPORE Collection\SporeBin\SporeApp.exe`, SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`, preferred image base `0x400000`. Addresses below are virtual addresses in that image. Analysis used PE section mapping and Capstone x86 disassembly of selected windows; it did not execute the original program. No REA server was available in this session, so these are direct byte/disassembly observations rather than REA evidence records.

## Lookup is exposed through an object vtable

The only exact little-endian absolute pointer to `414DC0` found in the file is at `13EB35C`. Constructor `403230` writes `13EB308` to the object at +0 (`403288..403294`); hence this entry is at vtable byte offset `+54`. The destructor-side path `4037C0..4037E6` writes the same table pointer. The constructor also initializes the lookup container at object +30 and passes the literal ASCII string `Editor/BlockData` at `13EB2DC` as one argument to `928A30` (`4032C0..4032EE`). That literal is a concrete editor-related registration/configuration lead, but its meaning and the scope of the object are not yet established.

The body `414DC0` uses the +30 lookup and dispatches to `414FC0` as documented in [the sample note](blockdata-native-sample-static-v1.md). A byte scan of executable PE sections for `E8 rel32` targeting `414DC0` found no direct call. This is a bounded scan, not proof that no call exists: virtual, indirect, tail-jump, dynamically resolved, relocated, or unrecognized paths remain. The vtable entry supplies a concrete next search target: find callers receiving this exact object/interface and dispatching slot +54, then trace their coordinate argument and both outputs. A raw search for all generic +54 calls without object provenance would not identify this consumer.

## Producer is reached through a multi-resource construction loop

The same executable-section `E8 rel32` scan finds `41C7DA -> 41A9E0`; the selected disassembly confirms it is a call. The enclosing function begins at `41C170` and prepares six values from globals at `41C530..41C561`, then iterates six groups (`41C5AD..41C5CF`) and a returned collection per group (`41C61E..41C64E`). The exact identity and semantics of those groups are unresolved. At `41C70F..41C730` it calls an object virtual +0C with a collection value, a selected group value and constant 4; a non-null result proceeds to `41A9E0` at `41C7DA`. The callee returns a byte status; failure skips this item. On success `41C802..41C84B` builds a resource key containing the selected values and type `5CAA5E28`, obtains a stream through virtual +34 and passes the generated buffer pointer and length through virtual +38 at `41C8EE..41C917`. The stream helper string `UTF/MemoryStream` occurs at `13EBADC` and is passed at `41C564`.

`41A9E0` calls `41AA40` with that source object and output buffer (`41A9FB..41AA06`). At `41AA4F..41AA66`, `41AA40` stores the source object and its first pointer; at `41AAAF..41AADC` it calls virtual +E8 on that first pointer with the source object, an array and bound `0x20`. On one branch it calls virtual +F4 at `41AB40..41AB6D` and iterates returned entries. This supplies concrete points to resolve the actual source object and its vtable; the argument meaning and generation algorithm remain unverified.

Two raw relative-call candidates to the producer's enclosing function are confirmed at `404E80` and `404E8E`: the former passes two values including a field at object +E8; the latter passes two zeros. Their enclosing control flow and object identity were not recovered in this pass, so they cannot yet establish when generation occurs. The constructor's `Editor/BlockData` literal is an editor-related lead, not proof that the generation call is exclusive to an editor or occurs during gameplay.

No coordinate meaning, terrain role, collision behavior, animation association, stage activation, or output consumer has been established. The most useful next static step is to resolve the lookup object's service/interface acquisition and virtual +54 call sites, while separately identifying the object passed through `41C730` to the producer. A negative direct-call scan must not be treated as a negative virtual-call result.

## Follow-up: service provenance and confirmed consumers

Factory `417CA0` is called at `5D7D30`. The result is retained at the caller object's +20 and passed at `5D7D64..5D7D68` to setter `4010C0`, which writes global `15D1C04`. Getter `401010` reads that global. This establishes the provenance needed to distinguish a lookup call from unrelated virtual `+54` calls, subject to later possible replacement of the global. A bounded scan of direct `E8` calls to getter `401010`, followed by disassembly of at most 150 bytes from each candidate, identifies lookup virtual calls at `44B34A`, `47230A`, `4724F4`, `4BBB5F`, `4CA01E`, `4F1444`, `4F3828`, `56A76A`, and `56A884`. This is not an exhaustive indirect-call graph: getter aliases and larger or non-linear paths were not covered. Two other textual `+54` matches were ordinary object-field accesses rather than lookup calls and are excluded.

At `56A720..56A76A` a concrete six-argument call takes two key words from input record +4 and +0, coordinate count from +90, and coordinate array address +94; two local 3-float triples are output. If the lookup returns success, `56A773..56A77A` calls `494ED0` on the consecutive triples. `494ED0..494EED` calls `41D9B0`, whose `41D9B6..41D9EE` computes component-wise second triple minus first. Then `56A77F..56A7AD` multiplies those three differences by the cube of record float +10 and writes the result through the caller's output pointer. This is strong static evidence that at least this consumer treats the output triples as opposing extents and computes a scaled box-like volume. The field +10's physical meaning and whether all dimensions are ordered remain unproven; wrapper success checks only the first axis. The coordinate array's meaning is still unknown.

A caller at `56A600..56A6F0` traverses a collection of records at container +98/+9C with stride `0x1D8`, calls that volume-like routine at `56A690`, multiplies each successful result by the record's +10 float again, and sums the weights. The later loop divides each weight by the sum and multiplies by the measured float constant 100.0 at `13F4B28`. Thus this caller computes normalized percentages from `(second - first).x * (second - first).y * (second - first).z * field(+10)^4`, when its arithmetic preconditions hold. Failed lookups store zero. This is a conditional static inference from the two routines, not a proven gameplay stat or asset classification; division-by-zero and nonfinite cases were not analyzed. Direct calls to `56A600` appear at `561476` and `563AC7`; resolving those callers and the 0x1D8 record type is the next concrete path to user-facing meaning.

The `Editor/BlockData` literal at `4032D2` is passed to `928A30`, whose inspected body initializes an internal allocation-like structure at the object +50 (`928A30..928A8F`). The literal is therefore not yet established as a service registration name. Service provenance is instead grounded in the explicit factory, setter and getter above.

They call global getter `67D7F0`, then its virtual +0C with the caller's key and an output handle (`5613C7..561424`, `563A30..563A84`). The separately traced [archive-index note](archive-index-native.md) identifies that global as a resource-manager object, but the exact resolved key and resource type in these call sites have not been established. On success both call `421A60`; its `421A7A..421A92` requests interface ID `03C609F8` through the returned object's virtual +0C. If the result is non-null, it becomes the container argument to `56A600`. This ties the `+98/+9C` collection to a resource-provider interface rather than an arbitrary global object, but does not yet prove a CreatureData or part-record identity.

The produced percentage array is then passed with that same interface to callback objects: at `5614C6..5614DD` through virtual +1C; at `563B11..563B28` through virtual +20, with a further caller argument. These are concrete next consumers for tracing the resulting values. The functions `561270` and `5639F0` themselves appear as pointers at `13F44D0` and `13F4444`, respectively; table ownership, callbacks, actual call timing and interface naming require further evidence. No gameplay/editor or part identity should be inferred solely from their proximity to source editor infrastructure.
