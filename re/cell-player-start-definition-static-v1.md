# Cell player start-definition resource chain

Static disassembly of installed `SporeApp.exe` SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a` and read-only package extraction; no original program, Cargo or GPU execution. This identifies a source-bound candidate, not the live mounted/selected player.

## Configuration-to-actor chain

At `137BA60..137BA95`, the static descriptor constructor registers `globals`, a 0x114-byte type whose hash is `2A3CE5B7`, at descriptor `016B1B3C`. Static table `015A8584` contains first word `A426730B` and second word `016B1B3C`. `E4CC40..E4CC64` feeds those two words to `E82450` and stores its returned handle at `015A858C`. `E4CCA0` passes this global handle to `E823D0`, which acquires the resource and returns the interface `02269ED1` +14 data pointer. Thus the relevant descriptor and raw table jointly point to the `globals` resource instance low word `A426730B`; actual runtime manager resolution, mounted packages and fallback remain separate.

`E750FD..E75102` calls `E4CCA0`; at `E751A8` it reads returned data +34 and passes that word to `E74A50` at `E751C0`. Its result becomes global player word +411C (`E751CB`). The actor constructor first calls `E4CAA0` with that supplied word (`E74A60..E74A6A`). Source schema initializer `137BFD2..137C00C` names field `startCell`, gives it offset +34 and native type 3, and supplies reference descriptor `016AE490`. Constructor `1375C30..1375C65` names that descriptor `cell` with size 0x31C; its registered type is `DFAD9F51` as documented by the existing [Cell schema/behavior trace](cell-behavior.md). The type-3 loader fixup replaces a nonzero source ID with an `E82450` handle, so the word read at runtime is a reference handle, not the raw integer below and not a direct final data pointer. `E4CAA0`/`E823D0` resolve that handle via the interface path described in [the handle note](cell-actor-pool-definition-handle-static-v1.md).

An executable-section direct relative-call scan found `E803D8 -> E750F0`. The caller passes pointer `015A8D3C` and a scalar computed in its preceding control flow. This is a static route, not proof of the conditions under which the call occurs or the position/scalar's meaning.

## Reference fixup and winner dependencies

A follow-up direct-instruction audit narrows the transition without selecting a live winner. In `E4AAD0`, a field descriptor supplies byte offset +08 and type +10. At `E4AB00..E4AB1C`, when the type is 3 and the four-byte field is nonzero, it calls `E82450(raw_field_word, descriptor+14)` and replaces that field with the returned handle; zero is left unchanged. For `globals.startCell`, the static initializer stores type 3, offset 0x34 and descriptor pointer `016AE490` (the `cell` descriptor). This fixes up a loaded copy; the original raw package bytes are not the resulting pointer.

`E82450` walks the list rooted at `016B54D0` and compares both the raw ID and the **descriptor pointer**, not merely an ID or decoded value (`E82468..E82470`). An existing pair returns the embedded handle at node +08; otherwise the helper creates and links a node and returns its embedded handle. The cache/list state, initialization and allocation validity are required inputs; raw ID equality across descriptor types does not imply the same handle. The native pointer/ownership behavior is not recreated by assigning the 32-bit source ID to an actor.

On handle acquisition, `E822F0` first calls `E82200`. For an ordinary nonzero/non-`FFFFFFFF` ID, `E82200` builds the three-word request `(handle ID, descriptor +08 type word, 0)` (`E82200..E82229`), then asks resource-manager virtual +14 and, if that fails, virtual +0C. `67D7F0`'s previously identified manager vtable `1437740` maps these to `8DD8A0` and `8DEC20`, respectively. `8DD8A0` walks provider entries at manager +9C..+A0, calling each virtual +18 until success. `8DEC20` enters the `8DE8A0` loading path; within the separately traced resolution path, `8DF1A0` consults a type mapping and a possibly supplied database, and its no-mapping/no-database branch uses `8DD930` to take the first registered database reporting the requested key. A failed primary attempt can enter `E82170`'s fallback route; no assumption is made that it is the same key or that it succeeds. Cached handle object state can bypass these steps entirely.

For a bounded, reproducible fixture, supply explicitly: the globals and Cell canonical keys and decoded bytes; ordered mounted database entries with signed priorities and registration order; the actual type-alias mapping or an explicit empty-map admission; optional supplied-database choice; provider/cache outcomes; and a declared fallback outcome. Under the admitted fresh, no-provider-hit, no-alias, no-supplied-database, successful exact-key path, compare candidates in the observed registered list order, choose the first matching record, validate the current 276-byte globals layout, translate its `startCell` type-3 ID to an explicit descriptor-bound symbolic handle, and repeat the same admitted resolution for the Cell key. With the two identical current globals copies this yields ID `CBCD1287`; the Cell bytes still depend on the explicitly supplied winning package. This is a deterministic fixture with declared admissions, not evidence of the original mounted winner, actual native pointer address or reachable player creation. The 264-byte legacy globals copy must yield unsupported layout rather than using the current +34 meaning.

The existing archive trace establishes that `8DE010` orders signed priorities descending and inserts after equal priorities, but the actual active-product package list, runtime registration order for ties, provider/cache state, type aliases, supplied database, fallback result and concurrent state remain unresolved. Those are not derivable solely from these three package files. A future original-source-bound comparison must separately capture or reconstruct those inputs before presenting a winner as retail behavior.

## Selective headless follow-up: call scalar

A separate Ghidra 12.1.4 `-noanalysis` import of the same hash-checked executable is retained at `target/ghidra-player-start-v1`; seeded functions `E7FD30`, `E4CC40`, `E4AAD0`, and `E750F0` all decompiled, with loader warnings and unresolved library links. Its manually seeded pseudocode is supporting evidence only. Direct PE bytes refine the caller scalar previously left open: `E8036F` executes `MOVSS` to load XMM0 from `014719E4`, whose low word is binary32 `40000000` (2.0); `E803A5..E803CE` loads current global +514C and executes `MULSS` by that XMM0 value, stores the result to the stack, and `E803D3..E803D8` passes position pointer `015A8D3C` to `E750F0`. Thus the supplied scalar on this branch is the source single-precision product of current +514C and 2.0, subject to MXCSR and memory/callback assumptions; it is not a fixed scalar. The decompiler associates the preceding +514C write with a table-selected value times 0.5, dependent on an input/state word; its selection, bounds and earlier provenance remain unverified here and must not be canceled algebraically under arbitrary floating-point conditions.

The earlier resource result remains conditional: `E4CC53..E4CC73` traverses records from `015A8584` to `015A8754` in 16-byte steps, passing each ID and descriptor to `E82450` and writing its result at the record's +8. `E4AB00..E4AB1C` handles nonzero type-3 loaded fields with the descriptor +14 and writes the returned handle back. These identify reference construction but do not establish mounted winner, provider/cache/fallback, runtime execution or player assignment. The two matching current-layout globals candidates identify `CBCD1287`; the differing Cell payloads and possibly other runtime sources prevent claiming a unique selected creation.

## Scalar ordering and upstream table gate

The `E803A5` `MOVSS` is the **first** +514C read: `E803B8` multiplies it by 2.0 and `E803BC` divides XMM1 by that result; `E803C0` stores the division result through `[[016B4BE8]+4C]`. `E803C5` then rereads through the previously computed address of +514C, and `E803CA..CE` multiplies this **second** read by 2.0 for the actor-creation call. The intervening store can alias the source location unless memory ownership excludes it; floating-point exceptions, environment and concurrent mutation also matter. There is no intervening call in this instruction window, although calls earlier in the enclosing function can affect its state. No cancellation or identical-read assumption follows.

The immediate +514C producer is now instruction corroborated. `E802A5` loads EDI from stack +3C in this point's current frame. `E802EF..E80321` selects fixed address `01484910` if EDI equals 1000; otherwise it starts at row `014846C4`, uses index zero for EDI below zero, and for nonnegative EDI walks successive signed threshold words, 28 bytes apart, until finding one greater than EDI. `E80328..E8033A` loads the selected row's +10 float, multiplies by binary32 0.5 at `01471B2C` and writes +514C; a reload of the global owner precedes the same XMM value's +5150 store. Bounds, table contents, input provenance and runtime state remain admissions; do not extrapolate a safe scan for arbitrary input.

An executable-byte scan for direct relative calls to `E7FD30` produced candidates `E806AF`, `E806CE`, `E808BC`, `E80B9C`, `E80FCF`; these are call-site leads, not a complete indirect-call census or proof of reachability. At `E80690`, current global byte +410C chooses between two argument sequences: nonzero passes zero as the first stack argument to `E7FD30`, while zero calls `E4EDC0` with the wrapper's stack input and passes that return as its first two arguments. Other call sites pass state from the object at global +5190, including +1C/+20/+24/+28, and global +410C/+4110. The meanings, initialized values, active callers and startup/save-state scheduling remain to be verified; this does not establish which route actually executes.

**Threshold indexing correction:** `E80304` initializes EAX to `014846E4` (base +20h), then the loop increments EAX by `1Ch` and ECX by one *before* its first comparison. Therefore its first threshold is `01484700`, equal to `014846C4 + 2*1Ch + 4`, and a failing first comparison selects row index 1 at `014846C4 + 1*1Ch`. Subsequent comparisons use `base + (index + 1)*1Ch + 4`; they are not the threshold at the selected row's own +4. A negative EDI selects row 0 without any comparison, while exactly 1000 bypasses the scan and selects `01484910`. The earlier phrase “successive threshold words” must be read with this indexing, not as a row-zero or row-one threshold test.

A standalone bounded model could take a caller-owned row/threshold slice, signed EDI, masked SSE policy and explicit memory/alias admissions, fail before an out-of-bounds scan, and expose the selected row and the ordered two reads separately. Such a model would be an inspection fixture until the stack input, owner identities, call reachability and memory environment are established; adding it alone would not connect source actor creation to the application.

The bounded Rust projection `cell_start_table_v1` accepts caller-supplied row values and thresholds, a distinct 1000 value, and the earlier DIVSS numerator. It returns selected row, +514C, division result and actor argument under scoped MXCSR 1F80, finite results, nonzero divisor, stable table and nonaliasing admission. Checked errors add safety and cannot reproduce native faults or sticky FP status. Five focused tests cover negative and boundary selection, exhausted table, special 1000 and invalid arithmetic. No executable bytes or application actor identity are admitted by the model itself. The source-player inspection now uses this model with an authenticated executable snapshot and an optional explicit progress input; its default remains zero.

The controlled `--source-player` inspection now accepts an optional explicit `--progress` in `0..=1000` (default 0). It reads a full executable snapshot, checks the existing executable digest on that snapshot, and reads the 22 rows and numerator from file offsets `1083AC4` and `10855D0` specific to that digest. It supplies the resulting +514C and argument-6 words to the existing candidate-size projection. This is an explicitly controlled input, not evidence of the original progress, actual state ownership, actor assignment, or live player. The calculation admits stable nonaliasing owners and restores MXCSR rather than preserving original sticky flags. Existing before/after file hashes do not guarantee atomic stability of other package reads.

A read-only PE-mapping check against the 20,447,744-byte, digest-matched executable verified the two file offsets above and thresholds 50 through 1000 in steps of 50. Across all 1001 explicitly bounded progress inputs, the scan selects row `progress / 50 + 1` for `0..999`, and the separate special address for 1000. This is a table snapshot check, not a native execution or observation of a runtime progress value.
