# Cell animation owner to model palette: conditional static path

This follows retained Ghidra dossiers for `SporeApp.exe`, SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. No runtime or native code was executed. All identities below are conditional static dataflow, not proof a live Cell actor follows the path.

`A0B110` (`target/rea/20261022-anim-rig-focused-v1/54-analyze_function.json`) constructs the CID via `9C5550`/`9C5130`. When its world +44 is nonzero, world byte +48 is set, and the relevant inputs resolve, it allocates a 0x3C `Anim/World/new_cmid`, stores it at CID +2C0 and calls either `9C7ED0` or `9C80B0`. A failed initialization frees the CMID and clears +2C0. It subsequently stores the CID at the request object +17C, the owning world at +190 and a new controller at +184. These are distinct objects, not interchangeable pointers.

`9C7ED0` (finalize-v2 dossier 220) stores its CID argument at CMID +0 and model-world argument at +4, with retention/release on replacement. On its successful resource-check branch it invokes that world's virtual +0C, installs the returned value at CMID +8 and returns whether that value is nonzero. `9C80B0` (finalize-v2 dossier 282) has a separate model setup path; do not conflate its arguments with the first path. `A06310` (source-runtime-v4 dossier 08) iterates pointers in its +24/+28 vector, tests each object's +64 byte, and calls `A04670` when its +17C is nonzero. In `A04670` (finalize-v2 dossier 202), the nonzero CID +2C0 branch invokes `9C6E40` with ECX equal to that CMID and a generated table buffer based at request object +190, +68. Its null +2C0 branch instead updates the distinct object +180 and returns. This bridges the same request object's CID into the palette producer on a conditional path; it does not prove scheduler reachability or pose correctness.

`9C6E40` (finalize-v2 dossier 198) checks CMID +8, uses CMID +4 as the virtual receiver, and calls receiver +98 with CMID +8, a count, and generated matrix pointer (or a null pointer on another branch). Independently, the constructor and vtable evidence indexed by `target/animation/model-world-prefix-native-evidence-v1.json` establishes table `0140D740` +98 = `744AA0`, forwarding over model animation LODs to `73B7C0`; that setter stores the generated pointer and clamped count. The conditional factory and world setup trace below resolves the receiver to `744AA0` under standard successful initialization, unchanged pointers and the described creation path. It does not establish a live actor or actual execution.

`740530` gathers the supplied generated prefix and group fallback matrices, and `743250` passes its resulting stack palette to `73A100` for CPU deformation (`cell-animation-request-palette-followup.md`). A separate conditional direct draw path in `73EDF0` uses graphics object +F0's +10 pointer when its +C count matches the draw context +4C; otherwise it chooses a static fallback. It offsets that base by the indexed 8-byte descriptor's first word times 48 and passes state 4 to `777990` before `11F94C0` draws. See `cell-gmdl-palette-render-state-v1.md` for the scoped descriptor ordering and limits. The conditional graphics +F0 alias to the corresponding LOD object is established below; the final shader state consumer remains unresolved. Neither path proves the other ran or that a generated table reached a particular draw.

The remaining high-value work is to establish the actual selected actor and resource, the active model/LOD lifetime and scheduling, palette count and pointer at draw, and the ultimate shader state consumer. Capturing runtime objects and vtables would supply separate observations, not substitute for source identity or lifetime checks.

## Conditional factory and graphics ownership closure

Raw PE x86 disassembly and table reads are scoped to the executable hash above. `67D8A0` reads `015FE8CC`; `7A77E0` (source-runtime-v6 dossier 154) obtains `74FD70`'s result and installs it through `67DAB0`; `7A65E0` clears it on teardown (dossier 153). `74FD70` allocates a manager and calls constructor `74FC90`, which stores vtable `0140D6D0`. The PE table's +14 is `753C10`: its `753C31..753C5D` allocates 0x8B8 and calls `753800`, whose `753859` installs `0140D740`; `753CAD` returns the constructed world. Thus, on successful standard graphics initialization, the named model worlds obtained through this factory have table `0140D740`, whose +98 is `744AA0`. Allocation failure behavior and later replacement are not established by this trace.

`67C660` reads `015FDC6C`. At `5D7BFE..5D7C34`, code obtains `A0BB10`'s result and installs it through `67C760`, clearing it after a failed initialization at `5D7C60..62`. `A0BB10` allocates a manager and calls `A0B860`, which installs vtable `01449B00`; table +20 is `A0BA80`. Its `A0BA8A..A0BAAA` allocates and calls `A09E70`, whose constructor installs `01449A80` (source-runtime-v3 dossier 361). That table +1C is `A05550` (dossier 360), which retains its first argument in animation world +44 and stores its second argument in byte +48. The Cell startup `E5D9E0` uses `67C660` virtual +20 to create `CellGame-Main` and `CellGame-Background`, then invokes each returned world's +1C with its respective Cell model world and second argument 1. Consequently, on successful standard initialization and absent later changes, `A0B110` receives a world whose +44 is that exact model-world pointer and +48 admits CMID creation; `9C7ED0` stores the same pointer at CMID +4. This proves a conditional original-code route to `744AA0`, not its execution by a specific actor.

The graphics alias is also narrower but concrete. `73AB00` (finalize-v2 dossier 177) retains its argument at graphics object +F0 and releases the previous value. `74A7F0` (source-runtime-v3 dossier 425) loads model graphics entries at +9C and calls `747270`. Bounded instruction decoding at `74739D..747410` shows the non-remapped branch walking model +9C graphics and +B4 LOD entries, then at `7473FE..747406` passing the corresponding +B4 object to `73AB00`; the remapped branch `747481..74748B` passes an indexed +B4 entry. The fallback model path in `74D3B0` likewise passes the +B4 entry to `73AB00` on the +9C graphics object at `74D699..74D6B8` (source-runtime-v3 dossier 403). `744AA0` forwards the generated pointer to these +B4 LOD objects. Therefore, where the same non-null LOD is chosen and the matching draw context count gate passes, `73EDF0` can select its +10 generated-table pointer through graphics +F0. The generated prefix count, fallback matrices, draw mode, active LOD, scheduling and ultimate shader upload still require evidence. The two branches are conditional, and no rendered frame was observed.

## Actor creation to animation object and resource

On the conditional player-start route `E803D8 -> E750F0 -> E74A50`, `E750F0` resolves the globals' descriptor-fixed `startCell` reference and assigns the returned actor handle to current player +411C. `E74A50` calls `E656C0` with the resolved definition handle at `E74E20..E74E67` and copies its returned triple into actor +FC/+100/+104 at `E74E6C..E74E94`. `E656C0` resolves the definition, then its structure handle, scans runtime rows in order, and on kind 4 passes the structure handle and row +0C list handle to `E65640`. A cache hit returns the cached triple without selection; a miss resolves the list and `E5C0F0` draws once per runtime row. For a selected type-0 row its result is `(row+04, 3D97A8E4, [015A8D0C])`; type 1 uses the separate `E84FA0` query route. Refer to `cell-kind4-cache-selection-static-v1.md` for exact order, conditions and arithmetic.

The pinned explicit PatchData start candidate has raw `startCell` ID `CBCD1287`, first structure row kind 4, and raw list ID `9A391385`. Its four type-0 rows have IDs `A1C46DF2`, `E219E5D0`, `E219E5D3`, `E219E5D2` and equal weight 1.0. This identifies four candidate first words, not the winning triple: descriptor fixup, selected definition/package, cache, RNG, global third word and later saved-player override are all material. `cell-player-start-definition-static-v1.md` documents the registered descriptor/type, provider searches and differences among installed copies. In particular the existing explicit fixture's second-row result uses synthetic seed and cache; it is not a recorded player.

At `E6DA7C..E6DAC5`, `E6D950` allocates a component handle, stores it in actor +248, resolves it and copies actor +FC/+100/+104 in order as the three-word `E5CCE0` argument (source-runtime-v6 dossier 800). `E5CCE0` chooses the background animation world at global +161C4 when its mode equals 1, otherwise main +161D0. At `E5CE46..E5CE75`, only when the triple's first word is nonzero and its second word is `3D97A8E4`, it passes the triple pointer and a structure-derived word to `E4EE10`, storing the result at resolved component +24. `E4EE10` calls the chosen animation world's virtual +30; on the standard table `01449A80` this is `A0B830`, a wrapper at `A0B830..A0B852` that forwards that triple as first argument to `A0B110`. The returned request object therefore flows into the same conditional CID and palette path above. `E6D950` next calls `E6D260` with state zero, and `E6D260` is gated by actor +FC and +248; the later state-dependent request path is detailed in `cell-actor-animation-request-trace-v1.md`. This is not proof that construction, virtual dispatch, or a particular request occurred in a live frame.

Resource lookup adds a second identity gate. `A0B110` calls `4BC760` with the triple, then calls `9CBFA0` on successful resolution; failure of that keyed route can return zero. Retained source-runtime-v3 dossier 298 shows that for the non-special group branch `4BC760` first asks resource-manager virtual +0C for `(triple[0], 0F43029A, triple[2])`, then on failure asks for the original triple. A special encoded third-word branch recursively clears its indicated flag bits before building a wrapper. The successful object supplies CSD/body construction in `9CBFA0` (anim-rig-focused-v1 dossier 55). This lookup is separate from the later AnimList request and ANIM lookup: neither the first actor ID nor a matching package key determines a mounted resource winner, request admission, animation binding or palette. Provider order, any cached CSD and save override must be known at the actual transition.

The retained `E6D950` dossier reports `E78C30` as its direct caller at `E78D15`. Bounded decoding of `E78C30` shows a call to `E5CC30` and additional branches involving the supplied definition +B4 and global state. On one surviving branch, `E78D07..E78D15` calls `E6D950` only when actor +248 is zero; a separate branch `E78D22..E78D2F` calls `E66090` when +248 is nonzero. This is a conditional component lifecycle lead, not proof of how often the scheduler invokes it or that a particular actor passed its gates. Direct-caller coverage does not rule out indirect entry or unrecognized calls.

On the player caller specifically, `E751E3..E7527F` supplies a further mandatory triple boundary after `E74A50`: it loads the object at current Cell global +5190. If that object's +0C equals 1, it copies its +10/+14/+18 words into actor +FC/+100/+104 even when the first word is zero. Otherwise, a nonzero saved +10 causes the same copy; if +10 is zero, it copies the constructor's actor triple into saved +10/+14/+18. In that non-1 branch it then passes the saved triple to `E829D0`, before later passing the actor triple to `E67A50`. This is a static branch description, not proof that the +5190 object is a particular persisted file or that either branch ran. Its creator, load/restore writers, lifetime and `E829D0` side effects are the next concrete evidence targets; without them the initial list choice alone cannot identify the player's final actor resource.

The two manager implementations, other side effects and message delivery are not established here.

A bounded raw PE candidate scan for direct displacement +5190 stores found `E6482A`, a constructor-region zero store; it is not a complete writer inventory, because adjusted base pointers, bulk copies and indirect stores can omit that displacement. The object creator, installation and load/restore writers are consequently not established. The immediate practical boundary is an explicitly identified P object with known lifetime and its current +0C/+10/+14/+18 words, plus an independently observed incoming event and scheduling order if the callback branch matters. No retained evidence supplies those runtime values. Original actor resource selection therefore remains conditional.
