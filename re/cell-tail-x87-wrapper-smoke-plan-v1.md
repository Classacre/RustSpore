# Standalone x87 wrapper smoke: review-only preparation

[The proposed host](cell-tail-x87-wrapper-smoke-review-v1.c) calls the independently reviewed wrapper DLL through the Windows loader with a single constant-returning, non-source thunk. This is a normal-return smoke test of a narrow wrapper envelope, not an execution of original instructions or a feeding comparison. The current source was compiled for linked inspection before the controlled smoke run below.

The host checks for an attached debugger and fails if either debugger API detects one or the remote check fails. It checks CPUID FXSR and SSE2 and the Windows SSE2 processor-feature flag, then allocates four distinct committed `PAGE_READWRITE` pages and verifies alignment and `VirtualQuery` before passing their first 512 bytes. A local result word is separate from those pages. The wrapper itself admits empty x87 stack and clean incoming status; unexpected caller state returns failure. The thunk returns one fixed EAX value and must be verified in the linked host to have a balanced cdecl return and no FP/SIMD effects. The DLL's loader must apply its relocations and the host must pass an absolute path to a separately hash-pinned DLL. The current source does not itself cryptographically authenticate a stable DLL or guarantee a debugger cannot attach after its check.

The host checks exact defined FCW, FSW, abridged FTW and MXCSR fields in the fixture, checks saved versus restored defined control/status/tag fields and eight XMM register byte ranges, and prints those fields for all four snapshots. It deliberately does not compare reserved bytes, empty x87 payloads, x87 instruction/data pointer or opcode fields, AVX upper state, or every OS extended-state component. Those omitted fields preclude a complete architectural-state restoration claim. The initial saved TOP/tag/status admissions must be met; an ordinary no-op thunk should produce no exception or stack-fault flags. Separate allocation and `VirtualQuery` checks do not create guard pages or eliminate races, and all pointers, thunk ABI, compiler behavior and normal fault-free completion remain admissions.

Before any invocation, independently review source, x86 compiler output, linked thunk and indirect DLL call, relocations/imports, CPU/OS feature checks and the allocation/cleanup paths. Build in a fresh directory without executing; capture and independently pin wrapper source/DLL, host source/object/executable, compiler/linker and build-observation receipts. Review a one-shot external runner that confirms all pins and a stable path immediately before and after the child, captures complete stdout/stderr/exit/timeout and does not retry. Source/model bytes are irrelevant to this no-source smoke except as separately named provenance. Confirm the runtime DLL path and loader policy, absence of a debugger, all printed snapshot checks, and no process sandbox or asynchronous fault recovery. Only after an independent review should this isolated child run. Failures, including an unsupported initial x87 state, must remain retained and must not be bypassed. No original source function is included in this preparation.

## Linked inspection artifact

The first compiled review artifact under `target/cell-tail-x87-smoke-review-v1` did not enforce an absolute path in the host itself; it remains retained and must not be run. The revised host verifies that `GetFullPathNameA` returns the exact supplied drive-absolute path and uses `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32`. The external runner must still pin the exact DLL before and after; path resolution and hashing do not prevent transient replacement. The source was compiled in the separate `target/cell-tail-x87-smoke-review-v2` directory.

The linked host is x86, SHA-256 `cc73645170fd09e40c4153dc60d792316096184c8b44a52d70931f028e734a84`. Its linked thunk at `00401010` is `mov eax,72A94B16h; ret`; the indirect wrapper call at `004012A8` is followed by `add esp,18h` and separate checks of wrapper status and thunk result. The intended wrapper DLL is x86, entry RVA zero, no PE imports, and SHA-256 `9afd99d82133e7e0c973ef0597ddc0d8bf4aef84849af5a5a5fd9c2f9795d236`. The host imports `KERNEL32.dll`; the DLL's PE relocations must be applied by the Windows loader. The host's import table alone does not pin the Windows runtime or loader. `linked-main.txt` and `build-observation.json` are retained; the receipt SHA-256 is `5cc87d86ea3a9be3aedeed0b5c6538474793d5d8f465d7e2866372eed1163c7c`. It records post-build hashes only and is not hermetic provenance. A separate linked-code and one-shot runner review remains required before execution. These checks cover a selected field-wise subset, not all architectural state.

The proposed one-shot runner creates its unique output directory and writes an `in_progress` receipt before verifying pins, so an ordinary preflight failure can be retained as `failed`. If path admission or directory creation fails, no receipt can be written; existing directories are never reused. A receipt-write failure also cannot guarantee a retained receipt. Output length is checked after subprocess capture, not by a streaming resource bound. The runner was independently reviewed before the one-shot run recorded below.

## One-shot result

After independent runner review, the standalone host and constant-return thunk ran once and passed with exit code zero; no original source instruction was executed. The selected FCW, FSW, abridged FTW, MXCSR and eight XMM register fields matched the host and runner checks, and the wrapper and thunk returned the expected values. `target/cell-tail-x87-smoke-results-v1` retains the result and receipt; stdout SHA-256 is `31004b0ebe5cb4e15595b993627d9796570a059986fc8392acd0c53c9ecd49be`, and stderr is empty (SHA-256 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`).

This is a normal-return, single non-source thunk check of the stated field subset. It does not establish full architectural state, AVX upper lanes, other x87 tag configurations, asynchronous fault recovery, source behavior or gameplay. The post-build provenance, stable-file, debugger-race, output-buffering and no-sandbox limitations above remain.
