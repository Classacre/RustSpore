# Cell gameplay bridge proposal: source health and feeding

This proposes a source-state integration boundary; it is not a patch or proof of a complete playable source Cell stage. Static executable addresses below refer to installed `SporeApp.exe` SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. Existing evidence and independent comparison limitations remain in [cell-behavior.md](cell-behavior.md), [cell-feeding-event-dispatch-v1.md](cell-feeding-event-dispatch-v1.md), and [cell-feeding-selector-source-trace-v1.md). No game, GPU, UI or Cargo code was run for this proposal.

## Mechanic with an actionable source boundary

The strongest candidate is the **integer actor +244 health field and the admitted selector-1 feeding consumer**, not the experimental simulation's float health. The retained `target/source-cell/native-cell-eating-sdk.asm` shows `E7D0A0` reading resolved player +244, looking up the selected definition unless its handle matches the special global, invoking effect calls before the numeric branch, when health is below six and the definition's signed `cEatData.hpValue` is positive, adding that value (twice when difficulty code is zero), then clamping that word to six. A present definition with `foodValue == 0` exits after healing; an explicit special/null definition uses food amount ten. `cell_feeding_route_v2` implements this slice with explicit admissions and separates zero-food cleanup and later call effects. Its accounting successor `cell_progression_v1` has a 1,504-case isolated native comparison; neither check validates the full feeding event or callback effects.

Additional executable-byte observations connect the field to actor lifecycle and damage. `E74A50` resolves an input definition at `E74A6A`, allocates and resolves a pool actor at `E74B01..E74B1E`, and writes integer six to that actor +244 at `E74F2D`. It also writes a word to +108 at `E74EBD`; its complete creation conditions and later writes still require tracing. `E5C400..E5C422` independently resolves the global player ID through `B71CC0` and sets its +244 to six if the resolve succeeds. This is a conditional reset function, not evidence of when it runs. At `E7A84C..E7A8A3`, a positive `E58800` result is subtracted from actor +244 and the result is clamped below at zero; a player-related conditional calls `E622F0` before the subtraction. The meaning of the damage calculation, subsequent calls, reachability and full death route remain unresolved.

The source event chain is stronger than a generic food collision: `E7E160` selector 1 forwards the record to `E7D830`, which requires a resolved actor and nonzero gate; `E7D790` reaches `E7D0A0` only when that actor ID is the current global player ID. Event callback `E7DBB0` may first invoke `E7D8B0` and mutate the player or save state. Consequently a snapshot taken before that callback is insufficient for the numeric consumer.

## Actual code gap and integration proposal

`crates/spore-bevy/src/cell_game.rs` runs `CellWorld` for `--experimental --cell`, including when source artwork is selected. `crates/spore-core/src/cell.rs` stores `CellActor.health` and `max_health` as prototype f32 values and its `feed` removes abstract `CellFood` using `Diet::can_eat`, growing by the food's floating mass. `CellWorld::progress()` derives a fraction from mass, and `CellWorld::step()` uses prototype damage and an evolution-mass threshold. Source art selection alone supplies neither the native actor pool state nor a verified source feeding record. `SourceCellLibrary::definition()` resolves an explicitly named Cell record using an inspection package order and also requires a structure and baked creation; it is not a verified native runtime definition/overlay resolver for all edible objects.

A concrete next patch should add a **source-mode actor/event state to the actual Cell update path**, initially gated on real source event admission, with integer +244 and a stable definition identity. On actor creation, apply the observed initialization only after the corresponding actor-pool creation route has been established. At a selector-1 dispatch, re-resolve the current actor/player and consumed definition after the callback, obtain the native signed difficulty and fresh snapshots, run the source pre-heal slice in order, and commit health to that same source actor. Route nonzero food through the source-byte branch and post-intervening-call accounting only after its `E514B0`, conditional `E532C0` and `E79750` effects are modeled or independently supplied at their actual boundaries. Preserve zero-food as an explicit pending cleanup path. UI should read this source integer state when source mode is active; the experimental f32/mass simulation remains separately identified.

Do **not** invoke that source consumer for a prototype `CellEvent::Ate`, map `CellFood.mass` to `foodValue`, map diet names to source `cellType`, or claim that the inspection package order is retail resolution. Those associations are unproved. A source path that cannot admit the required event should return an explicit unsupported/pending result rather than silently perform the prototype update as if it were original.

## Remaining link and acceptance evidence

The decisive remaining link is the producer-to-dispatch bridge: reconstruct feature geometry and ordered `E6A450` / `E6A2B0` selection and `E59B40` arbitration; preserve the reverse actor pass; trace event creation gates and pool-handle lifetime through `E7E6F0` and callback; then prove that the consumed actor's +108 handle resolves to the source definition used at `E7D0A0`. Also establish actual actor creation/player assignment, resource overlay/fixups, difficulty source, effect calls and `E79750` mutations before enabling the full route. The current renderer and input paths do not yet provide these values.

A real integration test should drive the actual source-mode update with an asset-backed actor and admitted event, check +244, routed food amount and progress state against an independent source-bound oracle, and verify zero-food, difficulty, player/nonplayer, callback mutation and stale-handle cases. Follow with a headless running-application check through the real Cell input/update and installed resources. A supplied event fixture verifies only the handoff under its stated admissions; it does not by itself prove live contact, runtime timing, full effects, or 1:1 gameplay.

## Additional player and event identity trace

The following is direct executable-byte disassembly, with the same executable hash as above. It strengthens the construction-to-dispatch identity chain without establishing runtime reachability.

- In `E750F0`, `E4CCA0` returns an object whose +34 word is supplied as the fourth stack argument to `E74A50` at `E751C0`. The returned handle is written directly to global Cell state +411C at `E751CB`, then resolved through pool global +1C via `B71D00` at `E751DE`. Inside `E74A50`, the fourth argument is passed to `E4CAA0` for definition resolution at `E74A60..E74A6A`; the same function allocates/resolves its actor and initializes its +244 word to six. The source of the `E4CCA0` object's +34 word, its mounted resource, and the conditions calling `E750F0` remain open. Do not conflate the returned handle with an object pointer or assume every `E74A50` caller assigns a player.
- `E7E820` resolves the first and second words of the selected contact record through the actor pool at `E7E82F..E7E851`, placing those objects in EBX and EDI respectively. On the case-10 route `E7EF1F..E7EF28`, EBX is passed as the first actor, EDI in ESI as the second actor, with raw word 2 and the contact record's +0C word. In `E7E050`, the eligible path passes first actor ID, second actor ID, raw word and second actor's +108 word to `E51D40`. The record constructor stores them at +28, +2C, +38 and +3C, respectively (`E51D6F..E51DC0`), and the caller installs callback `E7DBB0`. These identities refer to that construction path and can be changed by intervening operations; they do not prove that arbitrary later record bytes still identify the same objects.
- The case-10 creation path requires second actor +179 to be zero, second actor +111 not equal to one, second actor +17B zero, first actor +178 zero, and `E572E0(first, second)` to return zero (`E7E050..E7E095`). A nonzero +179 takes a path returning true without establishing event creation. These gates must remain ordered; their semantic names and wider effects are not established. Case 9 has a separate route and cannot be replaced by this case-10 predicate.
- During callback, if the second actor's ID equals the current player and save +E8 is nonzero, `E7D8B0` writes the first actor's ID to player +411C (`E7D8C1..E7D8E8`) before later dispatch checks. A consumer must therefore resolve current player identity after callback and use the current event fields, not cache the player from contact time. `E7F9E0` also clears +411C before its cleanup pass; this is another reason not to treat handles as stable across lifecycle transitions.

These observations enable an explicit source actor identity/state representation and make the record handoff concrete. Remaining integration gates include tracing `E750F0` reachability and the actual config +34 resolution, producer selector and contact geometry, callback side effects/aliasing, case-9 gates, source event scheduling and pool lifetime, and resource overlay resolution. The observed branch chain still does not justify emitting source selector-1 events from the experimental simulation's abstract food collisions.

## Pair source, strict overlap, and update order

A further bounded trace connects the case-10 candidate to the local update path. In `E80C75..E80C98`, startup calls `BBB820` with two literal `0x1000` arguments and stores the returned pointer at global Cell state +4104. Actor creator `E74A50` conditionally calls `BBB7F0` with that collection, the actor's first word and two locally constructed vectors; the return is stored at actor +364 (`E74FD0..E75036`). `E6DBB4` and `E6E0F1` pass the same collection to `BBBD10`, and `E7813F..E78146` passes the +364 value to `BBB800` after checking it against -1. The exact collection implementation, registration conditions, insertion failure semantics and ordering have not been recovered. It is not yet safe to synthesize its pairs from an unordered list.

At `E7F290`, iteration over +4104 obtains a pair of words and uses `B71CC0` to resolve both against the actor pool; failure of either skips the pair. It calls `E6D7F0` for each resolved actor to supply a vector and scalar, then calculates squared 3D distance and squared sum of the two scalars. `COMISS` followed by `JBE` invokes `E7F170` only when the squared sum is **strictly greater** than squared distance; equality and unordered comparison skip. This is the broadphase gate, not complete feature contact geometry or proof that either scalar is a fixed authored radius. The precise arithmetic order and runtime floating-point state matter at thresholds.

`E7F170` rejects equal actor IDs, resolves both +108 definition handles using `E4CAA0`, and requires both resolved definitions' +B4 words nonzero. Subject to valid resolutions it runs `E73E10` first with the original actor/definition order and then with both reversed, sharing one selection record. It dispatches `E7E820` only if the resulting selector is neither zero nor hexadecimal `16`. For a concrete selector-10 candidate, the existing `E6A450` trace describes, among other paths, feature code 2 on A, definition +B4 code 2 on B, relation 0, and both actors' +112 bytes zero, **after all earlier exits**. `E59B40` submits that candidate to the shared record; a later candidate in either ordered pass or the `E6A2B0` tail may win. This is a conditional candidate, not a rule that a broadphase overlap emits a feeding event.

In the straight-line segment of `E7F3D0`, `BBB810` on +4104 runs at `E7F501`, followed by `E52940`, `E59D00`, event-pool traversal `E7E7D0` at `E7F521`, `E7C8F0`, `E5ADB0`, `E7ADA0`, and then the pair/contact pass `E7F290` at `E7F54A`. This proves call order in this segment. It does not establish wall-clock cadence, rule out direct dispatch elsewhere, or prove an event created by the contact pass survives until any later traversal. A source-mode update should preserve the verified order only after its caller and the intervening routines' mutations are modeled; it must not immediately consume a newly selected contact by assumption.

The concrete wireable pieces are the typed actor-pool handles, the source +244 state and definition handle, strict broadphase test, ordered two-pass record and existing `E59B40` arbiter, and the case-10 record fields/gates. Their actual use needs the collection's pair-production and lifecycle semantics, `E6D7F0` inputs, all feature geometry and ordered evaluator/tail side effects, then event scheduler/callback behavior. Until these are available, their use in a source-mode update must stop at an explicit unresolved boundary instead of substituting the prototype's distance/diet collision.

## Pair collection and geometry getter: further static trace

`BBB820`, `BBB7F0`, `BBB800` and `BBB810` are one-instruction jumps to `BBAE20`, `BBAB40`, `BBAC30` and `BBAD00` respectively. The factory allocates a 56-byte object, a pair buffer of eight-byte entries, a 16-byte-per-slot object array and endpoint arrays. The two startup arguments are both `0x1000`; the creator stores the second argument as the pair capacity at object +00 and the first at +04. Allocation failure, capacity enforcement for object registration, and exceptional arithmetic have not been established.

`BBAB40` takes a collection, an ID word, two two-float endpoint vectors and a separate tag word. It allocates either a fresh slot or a free-list slot, stores ID/tag in its 16-byte slot, appends two endpoint records for each of two axes, and returns the slot index. In `E74F5B..E75036`, actor creation first calls `E6D7F0` for center and scalar. Registration happens only if its supplied word at the relevant stack location equals Cell global +40FC; otherwise actor +364 is set to -1. On the registering branch it passes actor ID and two 2D points formed from center X/Y minus and plus the scalar. A supplied tag of -1 is replaced by -5 for definition +B4 equal to 5 or 7, or another supplied value otherwise. These exact values and comparisons do not yet establish their gameplay names.

`BBAC30` removes a slot by marking all four associated endpoint entries with the signed short value -2, returning the slot to a linked free list and reducing the live count. Actor cleanup's `E78130..E7814B` reaches `BBB800` only if +364 is not -1. The earlier `BBBD10` calls operate on the collection during actor movement, but the complete input/update rules and all mutation ordering still need separate tracing.

`BBAD00` calls `BBA7C0` for both axes to merge endpoint storage; the latter uses an imported sort with comparator `BBA700`. It then walks the axis-zero endpoint array and keeps an active list of slot indices. For each opening endpoint, it tests each active slot through `BBA9C0` with axis zero omitted: that test rejects equal nonzero tags, then rejects if the axis-one endpoint ranks are disjoint. On accepted pairs, `BBAD9D..BBADBF` checks the pair buffer count against capacity; if equal, the candidate is skipped. It compares the two ID words as **signed** integers and stores the lesser first in the pair entry. Closing endpoints remove the corresponding active slot by swapping in the final active-list entry; this changes later pair enumeration order. Equal or unordered endpoint ordering is not established: `BBA700` returns -1 or +1 and does not return zero for equal floats, so sorting ties cannot safely be replaced by an assumed stable order. Overflow behavior of the bounded local active-list storage also remains to be established.

`BBAB30` returns pair count minus one. `BBB840` clamps its supplied cursor to count minus one, stores one less back into the cursor, and returns the indexed eight-byte pair when nonnegative. Thus `E7F290` consumes the **stored pairs in reverse array order** for a stable array. The order of storage depends on endpoint sorting, active-list mutation, insertion/update history and capacity; signed sorting within each pair does not sort the pair list. Mutation or invalidation while iterating is not established. This is a concrete obstacle to replacing the source collection with an unordered collision set.

`E6D7F0` has two geometry paths. With actor +FC zero it returns the three words at +4C/+50/+54 as center and copies +58 as scalar. Otherwise it calls `E67A50` using the actor's +FC/+100/+104 triple; its result supplies a center at +1238/+123C/+1240 and a scalar at +1244. The returned scalar is multiplied by actor +58. If actor +48 bit 1 (`& 2`) is set, the center is first multiplied by the 3-by-3 float arrangement at actor +5C..+7C; it is then multiplied by +58 and translated by actor +4C..+54. Each operation follows the observed scalar SSE instruction order at `E6D83A..E6D942`. This specifies how the broadphase inputs are constructed if the referenced object and actor fields are valid; the identity/lifetime and update of the `E67A50` result and the source of those actor fields remain open. It does not make the two-dimensional collection test equivalent to the later strict 3D contact test.
