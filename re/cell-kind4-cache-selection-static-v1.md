# Cell kind-4 cache and weighted selection boundary

Static Capstone x86 trace of installed `SporeApp.exe` SHA-256 `17cf32b3e3adbcc7ed9c4e593c83b5d3deb3c675059b7ad9cbfd19192df5f87a`. This follows the explicit candidate records in [the constructor note](cell-start-actor-constructor-static-v1.md). No original program, Cargo, GPU or game execution was performed; package/provider choice and runtime pointer identities remain unobserved.

## From constructor to cache key

`E74E20..E74E67` reloads the supplied definition-handle word, passes it to `E656C0` with a three-word output, and later copies that result into actor +FC/+100/+104 (`E74E6C..E74E94`). `E656C0` resolves that definition through `E4CAA0`, then resolves its first field (the structure handle) the same way. It traverses the resulting structure's runtime array at +14, count +18, stride 0x28, in row order. It stops on the first kind 3, 4 or 5; kind 1 is not selected by this branch. On kind 4, `E65768..E6576F` calls `E65640` with **the structure handle word** as its first argument and the structure row +0C word as second argument. In the fixed-up runtime objects those are handle words, not necessarily the raw disk IDs or resolved data pointers. A cache key based solely on CELL ID, list ID, raw bytes or visual identity would be unsupported.

The explicitly selected PatchData candidate has raw structure key `CBCD1287:4B9EF6DC:00000000`, with first raw row kind 4 and +0C ID `9A391385`; its explicit list key is `9A391385:F9C3D770:00000000`, SHA-256 `29b0f195b26bf2480586518e385933284819ff360a991ea706a939717a5d5f8a`. The raw 120-byte list has four 0x1C-byte rows, each type 0 and weight f32 1.0, with +4 words `A1C46DF2`, `E219E5D0`, `E219E5D3`, `E219E5D2`. These disk joins do not prove runtime fixups, actual mounted winner, cached state, selection or active actor.

## Cache hit and miss

`E65640` uses the object at Cell global `[016B4BE4]+5170`. `810230` searches for the first argument using unsigned comparisons against the node key at +10; the sentinel comparison at `E65662..E6566C` decides hit versus miss. On a hit `E6566E..E6567D` calls `E650B0` for that same key and returns its value pointer; this branch does not call `E5C0F0` or directly consume RNG. On a miss `E6567E..E65694` calls `E650B0` first, obtains/inserts the value slot, then calls `E5C0F0` with the **second** argument and a local triple. It copies all three returned words into that cache slot and returns the slot pointer (`E65699..E656AF`). The search/insertion routine uses the first key word with unsigned ordering (`E650C6..E650E3`) and the insertion path sets up zero words before invoking `E63D10`. This means insertion precedes selection: a failed/aborted helper, reentrant access, allocation failure or concurrent mutation cannot safely be replaced by an assumed all-or-nothing cache transaction. The precise failure/lifetime semantics of `E63D10`, cache clearing and reentrancy remain unproved.

The cache key is the structure-handle word; the list handle is not part of the compared key. A hit therefore reuses the stored triple without rerunning weighted selection even if a supplied second handle differs, assuming the stable map and lifetime preconditions shown. Do not use that conditional observation to infer cache state or stale-object behavior in a live game.

## Selection loop and RNG

On a miss, `E5C0F0` resolves the supplied list handle through `E4CAA0`. It takes signed count at list +00 and runtime row pointer +04. An initial binary32 accumulator is zero and selected index is -1. For each row in increasing index order, it:

1. Loads the prior **stored f32** accumulator, adds row weight +08 in x87, stores the sum to the f32 accumulator without popping, then stores/pops the retained x87 sum to a binary64 temporary (`E5C136..E5C14A`). The two stores can differ; the next iteration reloads the f32 accumulator, not the binary64 temporary.
2. Calls RNG `935D40` using global RNG object `01602760` **once per row**, including the first row, then multiplies the returned x87 result by the binary64 temporary. It clamps the product against the total and zero via the displayed ordered x87 comparisons (`E5C153..E5C16B`).
3. Loads the current row weight, compares it against the clamped value, and replaces the selected index only when the weight is strictly greater (`E5C16D..E5C176`). After a row the loop continues even if it was selected. Equal and unordered behavior follows the exact `FCOMI/FCOMPI` flags; do not approximate it with a differently ordered weighted draw.

For an admitted finite positive four-row 1.0-weight candidate list, the code issues four RNG calls on a miss, not one draw for the whole list. In the admitted `cell_request_rng_v1` nonzero-state PC53/PC64 domain the initial row's random fraction is below 1, so that first row is selected initially; subsequent rows can replace it. The final selected row still depends on the subsequent fractions and actual control state. This statement assumes stable list and RNG and excludes source zero-state RDTSC behavior. A hit performs zero selection-loop calls. The size path and null-orientation path each separately call the same RNG earlier, but intervening constructor calls occur before `E656C0`; this audit has not established whether they or their transitive callees consume or mutate the RNG. Therefore those two earlier transitions alone do not prove the selection entry state.

If the list count is not positive or no index is selected, `E5C18D..E5C1A9` copies a three-word global default from `015A93A4..015A93AC`. For selected type 0, `E5C283..E5C2A0` returns `(row+04, 3D97A8E4, [015A8D0C])`. Selected type 1 instead enters `E84FA0`, with bounds adjusted according to Cell global +410C/+4110 when that branch is active; its query and conditional fallback have separate unresolved inputs. Other selected types use the global default. The local reference wrapper is released through `E82160` before return; pointer/handle lifetime, resource reload and effects require their own admission.

## Minimal integration/verification gate

An isolated fixture can take an explicit resolved structure-handle identity, list handle, cache contents and post-earlier-call RNG state; on a hit require the existing triple and no selection RNG, on a miss reconstruct the 0x1C row stream with exact f32/f64/x87 order, four recorded RNG draws and selected type-0 triple, then store it under the structure-handle key. It must explicitly admit stable map, successful handle/array resolution, valid rows, masked FP behavior and no reentrant mutation. Type-1 selection, unknown default words, fallback, allocation errors and special RNG state must be explicit unsupported paths unless independently supplied at their real call boundary. Native-byte host comparison and content-hash-bound list extraction are separate gates. A checked actor pool may not become a live source actor merely because this isolated triple is available; the prior resolver, cache/resource lifetime, all intervening constructor effects and later actor initialization remain necessary.
