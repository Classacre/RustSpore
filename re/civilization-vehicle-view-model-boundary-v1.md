It obtains an object via `B3D5C0` and invokes the new view's virtual +28 with that object, the caller-supplied object, the triple pointer and another caller-derived value. On the unchanged vehicle-view table this +28 is `E94A60`, which forwards four arguments to `E92810`. The exact identity and lifetime of the original object, returned interface, third-word scope, +90 predicate, lookup owner and returned triple are not established; this is a conditional dataflow, not a serialized vehicle key or live runtime choice.

## Key-to-model-side boundary

`E92810` obtains another interface from its first supplied object by virtual +0C with `01186577`, retains/replaces it at view +0C, and tests its virtual +AC result. It compares three words returned by that interface's +98 against the supplied triple at `E92889..E9289D`. If those differ, or other conditional checks do not accept the existing object, `E928B0..E928D2` passes the supplied triple to virtual +94 and then calls virtual +A0 with another supplied word. Only when its AL result is nonzero does the code reacquire virtual +AC; zero skips that reacquisition. If the model-side result is nonzero, it may transfer position words and invokes further object methods. The actual receiver/vtable, behavior of +94/+A0, provider resolution, loaded model type and object identity must be traced separately. A matching triple is not by itself proof of a selected GMDL or a successful draw. Zero/allocation-failure paths have additional native dereferences and are not admitted as safe.
